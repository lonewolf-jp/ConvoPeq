### 1.5 resetToDefaults() の扱い（v2.1 全面書き直し・監査修正 A の反映）

**呼出経路（v2.1 実測・3 経路）**:

```
(1) コンストラクタ経路      : EQProcessor コンストラクタ :131 → resetToDefaults()
(2) UI Reset 経路（実行時） : EQControlPanel.cpp:433 engine.resetEQToDefaults()
                              → AudioEngine.h:1318 { uiEqEditor.resetToDefaults(); }
                              → EQEditProcessor.cpp:116-119 { EQProcessor::resetToDefaults(); scheduleDebounce(); }
                              → EQProcessor::resetToDefaults()
(3) loadPreset 経路        : EQProcessor::loadPreset :318-320 → resetToDefaults()
```

v2 までの「resetToDefaults は Audio Thread 開始前のコンストラクタ経路のみ」という記述は**誤り**であり、UI Reset（**Audio Thread 稼働中に実行され得る**）と loadPreset 経路を見落としていた。本設計書で削除の対象とするのは resetToDefaults 内の AGC atomic publish 3 行（:246-248）であるため、**稼働中経路での機能的同一性**を証明する必要がある。

**削除根拠（v2.1・serial protocol による機能的同一性）**:

- resetToDefaults() は内部で **`requestAgcReset()`（Core.cpp:256）を呼び、`agcResetSerial` を前進**させる。Audio Thread は process() 冒頭で `agcResetSerialNow != rtSeenAgcResetSerial` を検知し、**`rtAgcCurrentGainShadow=1.0 / rtAgcEnvInputShadow=0.0 / rtAgcEnvOutputShadow=0.0` に自己更新**する（Processing.cpp:588-593）。
- つまり AGC 状態リセットの**唯一の実効伝達経路は serial protocol** であり、atomic 3 個への publish はこの経路に**寄与しない**（Audio Thread は 3 個を読まない・P-D2-1 §1.1）。
- したがって UI Reset 経路（Audio Thread 稼働中）でも、publish 3 行の削除は**機能的に同一**（serial protocol が shadow リセットを完結させる）。
- コンストラクタ経路では Audio Thread 未起動のため、shadow 初期値（EQProcessor.h:733-735 `{1.0}/{0.0}/{0.0}`）が既にリセット後の値と同一であり、publish の有無は観測に影響しない。
- loadPreset 経路も UI Reset と同一の serial protocol で吸収される。

**結論（v2.1）**: resetToDefaults() は 3 経路すべてで `requestAgcReset()` → serial 前進 → Audio Thread shadow 自己更新という既存機構を備えており、AGC atomic publish 3 行はどの経路でも機能的に冗長。削除は P-D2-1（§1.1）と本節の組み合わせで成立する。
