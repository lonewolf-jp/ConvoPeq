# BUG-065: EQProcessor::reset() fails to trigger AGC state reset — sets agcResetSerial to 0 instead of incrementing

**Status:** Open
**Severity:** Medium
**Component:** `EQProcessor`
**Files:**
- `src/eqprocessor/EQProcessor.Core.cpp` (reset function, line 276)
- `src/eqprocessor/EQProcessor.Processing.cpp` (process function, AGC reset check, line 586-593)
- `src/eqprocessor/EQProcessor.h` (requestAgcReset, line 539-542)

## Summary

`EQProcessor::reset()` sets `agcResetSerial` to 0 via `publishAtomic` and also writes `rtSeenAgcResetSerial = 0` directly. This defeats the AGC reset mechanism: the Audio Thread's `process()` function compares `agcResetSerial` against `rtSeenAgcResetSerial`, and when both are 0, no reset occurs. Additionally, `reset()` writes to `rtSeenAgcResetSerial` from the Message Thread, which is a data race if the Audio Thread is concurrently reading it.

## Detailed Analysis

### Correct pattern: `requestAgcReset()` (EQProcessor.h:539-542)

```cpp
inline void requestAgcReset() noexcept
{
    convo::fetchAddAtomic(agcResetSerial, static_cast<std::uint64_t>(1), std::memory_order_acq_rel);
}
```

This **increments** `agcResetSerial` by 1, guaranteeing the value changes. The Audio Thread detects the change and resets the AGC shadow state.

### Buggy pattern: `reset()` (EQProcessor.Core.cpp:275-279)

```cpp
convo::publishAtomic(bandResetPacked, static_cast<std::uint64_t>(0), std::memory_order_release);
convo::publishAtomic(agcResetSerial, static_cast<std::uint64_t>(0), std::memory_order_release);
rtDeferredBandResetMask.store(0, std::memory_order_relaxed);
rtSeenBandResetSerial = 0;
rtSeenAgcResetSerial = 0;
```

Two problems:

1. **No-op reset**: `agcResetSerial` is set to 0. If it was already 0 (or if `rtSeenAgcResetSerial` was also 0), the comparison in `process()` at line 587 (`agcResetSerialNow != rtSeenAgcResetSerial`) evaluates to false, and the AGC state is **not reset**. The shadow variables (`rtAgcCurrentGainShadow`, `rtAgcEnvInputShadow`, `rtAgcEnvOutputShadow`) retain their stale values from the last `processAGC` call.

2. **Data race on `rtSeenAgcResetSerial`**: `reset()` is a public method callable from any thread. It writes `rtSeenAgcResetSerial = 0` (a non-atomic member variable) from the Message Thread. If the Audio Thread is concurrently reading `rtSeenAgcResetSerial` in `process()` (line 587), this is a **data race** (undefined behavior).

### Audio Thread AGC reset check (EQProcessor.Processing.cpp:586-593)

```cpp
const std::uint64_t agcResetSerialNow = convo::consumeAtomic(agcResetSerial, std::memory_order_acquire);
if (agcResetSerialNow != rtSeenAgcResetSerial)
{
    rtSeenAgcResetSerial = agcResetSerialNow;
    rtAgcCurrentGainShadow.store(1.0, std::memory_order_relaxed);
    rtAgcEnvInputShadow.store(0.0, std::memory_order_relaxed);
    rtAgcEnvOutputShadow.store(0.0, std::memory_order_relaxed);
}
```

The Audio Thread only resets the AGC shadow state when `agcResetSerial` differs from `rtSeenAgcResetSerial`. Since `reset()` sets both to 0, the condition is false and the reset never happens.

### Same pattern in `prepareToPlay()` (EQProcessor.Core.cpp:786-790)

```cpp
convo::publishAtomic(bandResetPacked, static_cast<std::uint64_t>(0), std::memory_order_release);
convo::publishAtomic(agcResetSerial, static_cast<std::uint64_t>(0), std::memory_order_release);
rtDeferredBandResetMask.store(0, std::memory_order_relaxed);
rtSeenBandResetSerial = 0;
rtSeenAgcResetSerial = 0;
```

`prepareToPlay()` has the same issue, but since it's called when the Audio Thread is stopped, the data race doesn't apply. However, setting `agcResetSerial` to 0 is still fragile — if the initial serial was already 0, no reset will occur on the first `process()` call.

## Impact

1. **AGC state not reset**: After calling `reset()`, the AGC envelope and gain shadow variables retain stale values. The AGC will continue from its previous state instead of starting fresh from gain=1.0, input=0.0, output=0.0. This can cause audible artifacts (e.g., sudden gain changes) when the user expects a clean reset.

2. **Data race**: If `reset()` is called from the Message Thread while the Audio Thread is running, writing to `rtSeenAgcResetSerial` (a non-atomic member) is undefined behavior. This could cause the Audio Thread to read a torn value or stale value, leading to missed resets or spurious resets.

## Root Cause

`reset()` uses `publishAtomic(agcResetSerial, 0)` instead of incrementing the serial (like `requestAgcReset()` does). It also directly writes `rtSeenAgcResetSerial` from the Message Thread, bypassing the Audio Thread's ownership of that variable.

## Suggested Fix (NOT to be applied — bug report only)

In `reset()`, replace:
```cpp
convo::publishAtomic(agcResetSerial, static_cast<std::uint64_t>(0), std::memory_order_release);
rtSeenAgcResetSerial = 0;
```
with:
```cpp
convo::fetchAddAtomic(agcResetSerial, static_cast<std::uint64_t>(1), std::memory_order_acq_rel);
// Do NOT write rtSeenAgcResetSerial — let the Audio Thread detect the change and update it.
```

This ensures the serial always changes (guaranteeing the reset is detected) and avoids the data race by not touching `rtSeenAgcResetSerial` from the Message Thread.
