# BUG-050: EpochDomain::enterReader の HB 順序 — epoch store が depth++ の後にあり getMinReaderEpoch が stale epoch を読む可能性

- **発見日**: 2026-07-26
- **重要度**: MEDIUM（UAF は不可だが SafeStateSwapper との整合性に課題）
- **カテゴリ**: Lock-free / メモリ順序
- **該当ファイル**: `src/core/EpochDomain.h:106-129` (enterReader)
- **関連ファイル**: `src/core/EpochDomain.h:195-229` (getMinReaderEpoch)
- **関連ファイル**: `src/SafeStateSwapper.h:142-150` (SafeStateSwapper::enterReader — 問題なし)

## 症状

`EpochDomain::enterReader()` は以下の順序で atomic 操作を行う：

```cpp
// enterReader()
const uint32_t previousDepth = fetchAddAtomic(slot.depth, 1, acq_rel);  // [A] release
if (previousDepth > 0) return;
// ... residency timestamp store ...
const uint64_t epoch = currentEpoch();
publishAtomic(slot.epoch, epoch, release);  // [B] release (AFTER [A])
```

`getMinReaderEpoch()` は以下の順序で読む：

```cpp
// getMinReaderEpoch()
const uint32_t depth = consumeAtomic(slot.depth, acquire);  // [C] acquire
if (depth == 0) continue;
const uint64_t epoch = consumeAtomic(slot.epoch, acquire);  // [D] acquire
```

### HB チェーン分析

[A] release と [C] acquire は synchronize-with 関係を形成する（[C] が [A] の書き込んだ値を読んだ場合）。しかし：

- [B] は [A] の **後**（sequenced-after）に位置する
- [A] release の synchronize-with 保証は [A] より前の書き込みにのみ及ぶ
- [B] は [A] より後にあるため、[B] の可視性は [A] release → [C] acquire の同期では保証**されない**

### 結果

`getMinReaderEpoch()` が depth > 0（Reader が入っている）を観測しても、epoch はまだ更新されていない可能性がある。この時点の epoch は kInactiveEpoch（exitReader が直前に設定した値）または kReservedEpoch（registerReaderThread が設定した値）。

## UAF 可能性の検証

UAF が発生するには、Reader が使用中のポインタが Reclaimer によって解放される必要がある。

シナリオ検証：
```
1. Reader: enterReader → depth++ (acq_rel)
2. Reclaimer: getMinReaderEpoch → depth>0, epoch=kInactiveEpoch → skip（epoch が kInactiveEpoch なので）
```

EpochDomain の getMinReaderEpoch は `epoch == kInactiveEpoch || epoch == kReservedEpoch` でスキップする。そのため、stale epoch が kInactiveEpoch または kReservedEpoch である限り、この Reader は minEpoch 計算に含まれ**ない**。

minEpoch に含まれない = この Reader の保護がない = Reclaimer がより多くのオブジェクトを解放できる可能性。

しかし、enterReader の時点では Reader はまだポインタを取得していない（getState() は enterReader の後に呼ばれる）。そのため、Reclaimer が何を解放しても Reader は影響を受けない。

**結論: EpochDomain では現状 UAF にはつながらない。**

## SafeStateSwapper との比較

SafeStateSwapper::enterReader には同様の問題は存在しない：

```cpp
// SafeStateSwapper::enterReader() — kIdleEpoch (0) をフィルタに使用
const uint64_t currentEpoch = consumeAtomic(globalEpoch, acquire);
publishAtomic(readerEpochs[readerIndex], currentEpoch, release);
```

SafeStateSwapper は depth を持たず、Reader が非参加の場合は kIdleEpoch (0) が getMinReaderEpoch でフィルタされる。enterReader は depth がないため、上記のような HB 問題を抱えない。

## 問題の本質

EpochDomain の設計は「depth increment → epoch store」の2段階であり、この間に HB のギャップが存在する。SafeStateSwapper の設計は「epoch のみ」の1段階であり、HB ギャップは存在しない。isOlder の比較に使用する値が異なる（EpochDomain: minEpoch を currentEpoch 初期値に + 全 Reader の epoch；SafeStateSwapper: 同上）が、SafeStateSwapper のほうが原理的にシンプルで誤りの余地が少ない。

## 修正案

### 案 A: enterReader で epoch を先に store してから depth++（推奨）

```cpp
void enterReader(int readerIndex) noexcept override {
    auto& slot = readers[readerIndex];
    
    // 先に epoch を取得（currentEpoch の acquire で最新値）
    const uint64_t epoch = currentEpoch();
    
    // depth++ より前に epoch を publish（release で他スレッドに可視化）
    // HB: epoch release → depth++ release → getMinReaderEpoch depth acquire → epoch acquire
    // これにより epoch store が depth increment より前に見えることが保証される
    convo::publishAtomic(slot.epoch, epoch, std::memory_order_release);
    
    const uint32_t previousDepth = convo::fetchAddAtomic(slot.depth, 1, acq_rel);
    if (previousDepth > 0) {
        // ネスト: epoch を戻す
        convo::publishAtomic(slot.epoch, kReservedEpoch, std::memory_order_release);
        return;
    }
    
    // residency timestamp
    const uint64_t nowUs = ...;
    convo::publishAtomic(slot.residencyStartTimestampUs, nowUs, release);
}
```

ただし、この修正にはトレードオフがある：
- nested enter 時に epoch を kReservedEpoch に戻す必要がある（追記）
- ネスト頻度が高い場合は無駄な store が増える

### 案 B: 現状維持（安全であることが証明されている）

EpochDomain は AudioEngine の RCUReader（IReaderEpochProvider）経由で使用される。RCUReader::enter() は EpochDomain::enterReader を呼ぶ前に ownerToken CAS とスロット取得を行うため、実際には上記の HB ギャップによる問題は AudioEngine の処理パスでは発生しない。

## 補足

- 発見経緯: SafeStateSwapper と EpochDomain の2つの RCU 実装のメモリ順序を比較中に発見
- SafeStateSwapper が「epoch only 1段階」なのに対し、EpochDomain が「depth + epoch 2段階」であることが本質的な違い
- 現時点で AudioEngine の RCUReader パスでは UAF 不可。しかし、将来的に EpochDomain が直接使用されるパスが増えた場合、修正が望ましい
