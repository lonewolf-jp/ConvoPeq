# BUG-064: Float/Double output path ordering inconsistency — `applyFixedLatencyDelay` vs hard clamp

**Status:** Open
**Severity:** Medium
**Component:** `AudioEngine.Processing.DSPCoreIO` / `AudioEngine.Processing.DSPCoreDouble`
**Files:**
- `src/audioengine/AudioEngine.Processing.DSPCoreIO.cpp` (float path)
- `src/audioengine/AudioEngine.Processing.DSPCoreDouble.cpp` (double path)

## Summary

The float output path (`processOutput`) and the double output path (`processOutputDouble`)
apply `applyFixedLatencyDelay` at **different positions** relative to the final hard clamp
to `[-kOutputHeadroom, kOutputHeadroom]`. This causes the latency delay ring buffer to store
different value ranges depending on the processing mode, leading to inconsistent output
behavior between float and double modes.

## Detailed Analysis

### Float path (`processOutput`, DSPCoreIO.cpp)

Processing order (lines 519–528):

```
519: peakLimiter.processBlock(dataL, dataR, numSamples, kPLThreshold, kPLKnee);
521: applyFixedLatencyDelay(dataL, dataR, numSamples);
523-528: hard clamp → dstL[i] = static_cast<float>(jlimit(-kOutputHeadroom, kOutputHeadroom, dataL[i]));
```

`applyFixedLatencyDelay` (DSPCoreIO.cpp:307–339) **reads old delayed values into `dataL`/`dataR`**
(replacing the current values) and **writes the current (unclamped) values to the delay buffer**.
The hard clamp happens **after** the delay, so:
- The delay buffer stores **unclamped** values (peak-limiter output, which may not fully clamp
  if the limiter has a soft knee or numerical edge cases).
- When delayed values are read back in a subsequent callback, they bypass the hard clamp and
  are written directly to the output buffer.

### Double path (`processOutputDouble`, DSPCoreDouble.cpp)

Processing order (lines 710–746):

```
710: peakLimiter.processBlock(dataL, dataR, numSamples, kPLThreshold, kPLKnee);
712-737: hard clamp to [-kOutputHeadroom, kOutputHeadroom]
739: applyFixedLatencyDelay(dataL, dataR, numSamples);
744-746: copy dataL/dataR to output buffer
```

The hard clamp happens **before** `applyFixedLatencyDelay`, so:
- The delay buffer stores **already-clamped** values (guaranteed within `[-kOutputHeadroom, kOutputHeadroom]`).
- When delayed values are read back, they are already clamped and safe.

### `applyFixedLatencyDelay` internals (DSPCoreIO.cpp:307–339)

```cpp
for (int i = 0; i < numSamples; ++i)
{
    delayL[writePos] = dataL[i];          // write current value to delay buffer
    ...
    dataL[i] = delayL[readPos];           // read old delayed value (replaces current)
    ...
}
```

The function **replaces** `dataL[i]`/`dataR[i]` with the delayed value. Whatever is in
`dataL`/`dataR` at the time of the call is what gets stored in the delay buffer.

## Impact

1. **Float path**: If the peak limiter does not fully clamp (e.g., soft knee, numerical edge
   cases, or limiter bypass), the delay buffer stores values that may exceed `kOutputHeadroom`.
   On the next callback, these unclamped values are read back and written directly to the output
   buffer **without** passing through the hard clamp, potentially causing output samples to exceed
   the expected headroom and clip downstream.

2. **Inconsistency**: Float and double modes produce different output when `fixedLatencySamples > 0`,
   because the delay buffer content differs. This makes A/B comparison between modes unreliable.

3. **DC blocker difference**: Additionally, the float path's DC blocker (`processInput`,
   DSPCoreIO.cpp:250–251) calls `dc.inputL.process()` and `dc.inputR.process()` separately
   (mono per channel), while the double path's `processInputDouble` (DSPCoreIO.cpp:301–302)
   uses the same per-channel calls. The output DC blocker in `processOutput` (line 376–377) also
   uses per-channel `process()`, while `processOutputDouble` (line 602) uses
   `dc.outputL.processStereo(dataL, dataR, numSamples, dc.outputR)`. If `processStereo` has
   stereo-coupled behavior, this is another inconsistency.

## Root Cause

The float and double output paths were developed independently and the ordering of
`applyFixedLatencyDelay` relative to the hard clamp was not kept consistent.

## Suggested Fix (NOT to be applied — bug report only)

Move `applyFixedLatencyDelay` in `processOutput` (DSPCoreIO.cpp) to **after** the hard clamp
(lines 523–528), matching the ordering in `processOutputDouble` (DSPCoreDouble.cpp:739).

Alternatively, move the hard clamp in `processOutputDouble` to **after**
`applyFixedLatencyDelay`, matching the float path. The former is preferred since the double
path's ordering (clamp-then-delay) is safer — it guarantees the delay buffer only stores
clamped values.
