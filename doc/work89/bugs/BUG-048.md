# BUG-048: EpochDomain::detectStuckReaders — 最初の一致で break し重度の Stuck Reader を見逃す

- **発見日**: 2026-07-26
- **重要度**: LOW
- **カテゴリ**: 診断ロジックのバグ
- **該当ファイル**: `src/core/EpochDomain.h:397-473` (detectStuckReaders)
- **関連ファイル**: `src/audioengine/ISRRetireRouter.h:79` (delegate)

## 症状

`detectStuckReaders()` は条件評価の優先順位を実装しているが、最初に条件を満たした Reader で `break` するため、より重度の Stuck Reader が存在しても検出されない。

## 条件（優先順位順）

1. **Chronic Stuck** — `residency > 30秒`（epoch差不問、pendingRetire > 0）
2. **Warning Stuck** — `residency > 10秒`（pendingRetire > 0）
3. **Epoch Gap Stuck** — epoch差 > threshold AND `residency > 1秒`

## 問題となるシナリオ

```
readers[0]: depth=1, residency=15s, epoch=current-5    → 条件2 (Warning) に合致 → break！
readers[1]: depth=1, residency=45s, epoch=current-100  → 条件1 (Chronic) に合致するが未チェック
```

- `detectStuckReaders` は reader[0] の Warning を返す
- 運用者が Warning 相当の対処（単なるログ出力など）しか行わない場合、reader[1] の Chronic Stuck が放置される
- Chronic Stuck は quarantaine が必要なレベルだが検出されない

## 技術的詳細

```cpp
// EpochDomain.h:397-473
for (int i = 0; i < kMaxReaders; ++i) {
    // 条件1: Chronic → break;
    // 条件2: Warning → break;
    // 条件3: Epoch Gap → break;
}
```

各条件ブロックの最後に `break` があるため、最初に合致した Reader のみが報告される。これは `StuckReaderInfo` が単一 Reader を返す設計であることに起因する。

## 修正案

**案 A**: 3パスに分けて評価し、最も重度の条件を優先して返す。

```cpp
// Pass 1: Chronic Stuck
for (int i = 0; i < kMaxReaders; ++i) {
    if (depth > 0 && residency > kChronicResidencyUs) {
        // return Chronic info
    }
}
// Pass 2: Warning
for (int i = 0; i < kMaxReaders; ++i) { ... }
// Pass 3: Epoch Gap
for (int i = 0; i < kMaxReaders; ++i) { ... }
return info; // どの条件も満たさなければ empty
```

**案 B**: `StuckReaderInfo` を複数 Reader 対応に拡張する（将来の設計変更）。

**案 C**: 単一 Reader 報告の現在の設計を維持する場合、`i` の走査順を residency 降順に変更。

## 影響評価

- Low: 診断情報の不正確さ。Safety に直接影響せず。
- 実際の Audio Thread ブロッキングや UAF にはつながらない。
- しかし、実際に Stuck Reader が存在する場合に検出漏れが発生しうる。
