# BUG-049: quarantineFlags への並行 store 競合 — 即時隔離と遅延隔離の競合

- **発見日**: 2026-07-26
- **重要度**: MEDIUM
- **カテゴリ**: 並行性バグ / 不変条件違反
- **該当ファイル**: `src/core/EpochDomain.h:255-281` (quarantineReader)
- **関連ファイル**: `src/core/EpochDomain.h:307-339` (verifyReaderInvariants)

## 症状

2つの Coordinator スレッドが同時に `quarantineReader()` を呼び出した際に、`quarantineFlags` バイトへの atomic store が競合し、不変条件 (`kPendingQuarantineFlag` と depth==0 の同時成立禁止) が破られる。Debug ビルドでは `verifyReaderInvariants()` の assert が発火する。Release ビルドでは `getMinReaderEpoch()` がこのスロットを正しくスキップするため機能上の影響は軽微だが、診断上の整合性が損なわれる。

## 発生条件

以下のタイミングで2つの Coordinator が競合する必要がある：

```
Coordinator A: quarantineReader(i)
  ↓
  reads slot.depth = 1  (reader active)
  ↓
  sets quarantineFlags = kPendingQuarantineFlag (0x02)

Reader: exitReader(i)
  ↓
  fetchSubAtomic(depth, 1): depth 1→0
  ↓
  stores epoch = kInactiveEpoch

Coordinator B: quarantineReader(i)
  ↓
  reads slot.depth = 0  (reader just exited)
  ↓
  sets quarantineFlags = kQuarantinedFlag (0x01)
```

Coordinator A の 0x02 store と Coordinator B の 0x01 store が同一 `std::atomic<uint8_t>` に対して競合する。揮発性の 8-bit store であるため、最終値は 0x02 または 0x01 のいずれかになりうる。

### 結果 A: 0x01 (kQuarantinedFlag) が生存

正常。Slot は quarantine され、getMinReaderEpoch から除外される。exitReader の pending チェックは `(flags & 0x02) == 0` により false となり、何もしない。

### 結果 B: 0x02 (kPendingQuarantineFlag) が生存 ← 問題

`verifyReaderInvariants()` のチェック:
```cpp
if (isPending) {
    assert(depth > 0 && "pendingQuarantine set but depth==0: should have been promoted to quarantined");
}
```
- `isPending = true` (flags & 0x02 != 0)
- `depth = 0` (Reader は既に exit)
- **assert が発火！**

`getMinReaderEpoch()` での動作:
```cpp
if ((flags & kQuarantinedFlag) != 0)  // flags=0x02 → false, 通過
    continue;

const uint32_t depth = consumeAtomic(slot.depth, acquire); // depth=0 → skip
```

depth==0 のチェックにより、このスロットはスキップされる。**機能上は正しい** — pending フラグのみでは quarantine 扱いにならないが、depth==0 のフォールバックにより除外される。

## 不変条件の破れ一覧

| チェック | 結果 | 影響 |
|---------|------|------|
| `isQuarantined && depth==0 → epoch==kInactiveEpoch or kReservedEpoch` | OK（quarantined ではない） | なし |
| `isPending → depth > 0` | **FAIL**（depth==0） | assert 発火 |
| `!(isQuarantined && isPending)` | OK | なし |

## 修正案

### 案 A: compareExchange で競合を排除（推奨）

```cpp
// 即座 quarantine パス
uint8_t expected = 0;
if (convo::compareExchangeAtomic(slot.quarantineFlags,
                                  expected,
                                  static_cast<uint8_t>(ReaderSlot::kQuarantinedFlag),
                                  std::memory_order_acq_rel,
                                  std::memory_order_acquire))
    return true;

// CAS 失敗 → pending を OR で設定
if (d > 0) {
    convo::fetchOrAtomic(slot.quarantineFlags,
                          static_cast<uint8_t>(ReaderSlot::kPendingQuarantineFlag),
                          std::memory_order_acq_rel);
    return false;
}
```

これにより、`kPendingQuarantineFlag` の設定が CAS の成功後に行われるため、2つの Coordinator の 8-bit store が競合しない。

### 案 B: exitReader 側で depth==0 確認後に pending を直接 quarantined に昇格

```cpp
// exitReader の pendingQuarantine 確定ロジック（変更なしだが堅牢性は不変）
const uint8_t flags = convo::consumeAtomic(slot.quarantineFlags, acquire);
if ((flags & ReaderSlot::kPendingQuarantineFlag) != 0) {
    // CAS で quarantined に昇格。pending が 0x02→0x01 の途中で他スレッドが
    // pending を再設定する競合にも対応。
    uint8_t expected = flags;
    convo::compareExchangeAtomic(slot.quarantineFlags,
                                 expected,
                                 static_cast<uint8_t>(ReaderSlot::kQuarantinedFlag),
                                 std::memory_order_acq_rel,
                                 std::memory_order_acquire);
}
```

## 影響評価

- Debug ビルド：assert 発火によるクラッシュ
- Release ビルド：機能上の影響なし（depth==0 のチェックがクッションになる）
- 発現頻度：極めて低い（2 Coordinator の競合 + 正確なタイミングが必要）
- Medium とした理由：Debug ビルドでのクラッシュ可能性＋不変条件の破れが診断ツールや将来のコード変更で悪化するリスク
