**→ 2026-08-15 検証結果: MPSC 化は現時点で不要（単一 Producer が構造的に確定）。実装変更なし（コメント文書化のみ）。**

  - **Producer = CoordinatorLoop のみ**: `submitRecoveryRequest`（cpp:868）← `submitRecoveryIntent`（AudioEngine.h:4375）← `QuarantineIntentHandler::handle`（ProcessIntent.cpp:139）/ `RecoveryIntentHandler::handle`（ProcessIntent.cpp:168、**dead code** — 誰も intentQueue_ に Recovery Intent を push しない）。両 handler は `processIntent`（Threading.cpp:237・唯一の呼び出し元）→ `runCoordinatorPhase`（Threading.cpp:232・唯一の呼び出し元）→ `CoordinatorLoop::run`（ISRCoordinatorLoop.cpp:39・専用 juce::Thread）上で実行。
  - **Consumer = Builder Loop のみ**: `popRecoveryRequest`（rebuildThreadLoop）/ `takePendingRecoveryAdmission`（rebuildThreadLoop）/ `discardRecoveryRequestsOnShutdown`（stopRebuildThread、Builder join 後）。
- **SPSC 前提の確認**: `recoveryIntentQueue_` は `LockFreeRingBuffer<RecoveryIntent,256>`（LockFreeRingBuffer.h 明示: SPSC・"Do NOT rely on this pattern for multi-producer/consumer scenarios"）。
- **対照（intentQueue_）**: 既に `MpscBoundedRing`（MPSC）— **複数 Producer（Builder/Rebuild・Timer・CoordinatorLoop deferred resubmit）が実在**するため（h:672）。

- **決定**: 現行アーキテクチャでは複数 Producer が存在しないため MPSC 化しない。単一 Producer 不変条件をヘッダー（recoveryIntentQueue_ 宣言）と cpp（submitRecoveryRequest）に文書化。**MPSC 化のトリガーは「将来 Timer 等から直接 submitRecoveryRequest を呼ぶ経路の追加」のみ。**
