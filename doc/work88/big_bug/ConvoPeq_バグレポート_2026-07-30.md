## 2. 新規に確認したバグ（要修正・パッチ付き）

### バグA【高】nucHCMode/nucLCMode がセッション永続化から欠落

`ConvolverProcessor::getState()`（`ConvolverProcessor.StateAndUI.cpp` 202–248行）が `juce::ValueTree` に書き出すプロパティを全て列挙すると、`phaseMode / useMinPhase / mix / bypassed / smoothingTime / irLength / autoDetectedIRLength / irLengthManualOverride / mixedF1Hz / mixedF2Hz / rebuildDebounceMs / experimentalDirectHeadEnabled / tailMode / tailStartSec / tailStrength / tailL1L2Multiplier / targetUpgradeFFTSize / enableProgressiveUpgrade / maxCacheEntries / irPath` の19項目で、**`nucHCMode`・`nucLCMode` が存在しません**。対応する `setState()`（289–387行）側にも `v.hasProperty("nucHCMode")` 等の読み取りが一切ありません。

一方 `pendingOverride.nucHCMode` / `pendingOverride.nucLCMode` は実行時の設定値としては正しく保持されており（`setNUCFilterModes()`, 812–835行, で読み書きされる）、UIから変更した値は稼働中は正しく反映されます。**しかし保存→再読込（プリセット/セッションファイル）を経由すると、この2値だけが黙ってデフォルト値に戻ります。**

これは前回セッション（2026-07-18解析時）で確認済みだった不具合で、今回のソーススナップショット（2026-07-28生成）でも**未修正のまま残存**していることを確認しました。

**修正**: `getState()` に `nucHCMode`/`nucLCMode` の書き出しを追加し、`setState()` 側に `tailMode` と同様の `juce::jlimit` によるクランプ付き読み込みを追加、`setNUCFilterModes()` を呼び出して反映します（`HCMode` は `Sharp=0..Soft=2` の3値、`LCMode` は `Natural=0..Soft=1` の2値であることを `OutputFilter.h` で確認済み）。詳細は `patches/ConvolverProcessor.StateAndUI.cpp.patch` を参照してください。

### バグB【高】RetireIntentオーバーフロー時の「最後の砦」に生成側が存在しない

`ISRRetire.cpp` の `RetireRuntime::emitRetireIntent()` を読むと、RetireIntent（DSPスロット解放要求）は以下の順でエスカレーションします。

1. メインVyukov MPSCキュー（容量256）へのバウンデッドスピン試行
2. 失敗時: Fallbackキュー（容量4096、mutex保護）へ
3. それも失敗時: `overflowRing_->tryPush()`（`RetireOverflowRing`、容量16384、SPSCロックフリー）へ
4. **それも失敗（または `overflowRing_` が null）時: `droppedIntentCount_` をインクリメントして無条件ドロップ**

一方 `RuntimePublicationCoordinator`（`ISRRuntimePublicationCoordinator.h/.cpp`）には、上記4段階よりさらに手前で介在するはずの `coordinatorDeferredRing_`（容量1024の `LockFreeRingBuffer`）と `lastResortQueue_`（容量4096の生配列、約160KB）が定義されており、`drainOverflowRing()` 内に両者から取り出して `retireRuntime.emitRetireIntent()` へ再投入する完全な消費（drain）ロジックが実装されています。

しかし、コードベース全体（`grep -rn "coordinatorDeferredRing_\|lastResortQueue_\|lastResortCount_"`）を検索しても、**これら2つのメンバへ書き込む（push する）コードが一切存在しません**。`ISRRetireRouter::enqueueWithRetry()`（`ISRRetireRouter.cpp`）も含めて確認しましたが、どのエスカレーション経路もこの2つのメンバに触れることはなく、`lastResortCount_` は `{0}` で初期化されたまま増加する箇所がありません。

**つまり、「OverflowRingが満杯になった場合の更なる安全網」として実装されたはずの2機構は、現状では到達不能なデッドコードです。** RetireIntentがOverflowRingからも溢れた場合、実際にはこれらの安全網を経由せず即座にドロップされます（オーディオDSPスロットの解放要求が失われる = 該当スロットのメモリ回収タイミングが遅延する可能性があります）。

副次的な問題として、`lastResortQueue_` は cppcheck が `uninitMemberVar` として指摘した通りコンストラクタで初期化されておらず、`RetireIntent::dspSlot`（"空き"判定に使う `UINT32_MAX` センチネル）が不定値になります。現状は `lastResortCount_` が恒久的に0のため到達しない箇所ですが、将来producerが実装された際の地雷になり得ます。

**今回のパッチ範囲**: 配列の値初期化（`{}`）による未定義動作の芽の除去のみを安全に実施しました（`patches/ISRRuntimePublicationCoordinator.h.patch`）。**「どの条件でproducerを起動すべきか」（OverflowRing満杯時に即座にここへ回すのか、一定の滞留時間を超えたエントリのみ回すのか等）は設計判断が必要なため、今回は実装していません。** 少なくとも「安全網が実際には機能していない」という事実の確認と、UB要因の除去を優先しました。

### バグC【中】fastTanh / musicalSoftClip の三重独立実装（Single Semantic Source違反）

`FastTanhApprox.h` 自身のコメントに明記されている設計方針は次の通りです（意訳）：「DSPCoreDoubleのSoftClipとEQProcessorのSaturationは全て同一実装を参照する（Single Semantic Source）」。

実態を `grep -rn "10395"` で確認したところ、高次Padé近似の係数（10395.0 / 1260.0 / 21.0 / 4725.0 / 210.0、閾値4.5）が以下の**3箇所に独立してハードコード**されていました。

| ファイル | 実装形態 |
|----------|----------|
| `FastTanhApprox.h` | ✅ 正規実装（`SoftClipPadéPolicy`、テンプレート経由） |
| `AudioEngine.Processing.DSPCoreDouble.cpp` | ✅ 正規実装を `convo::dsp::fastTanh<SoftClipPadéPolicy>` で正しく参照 |
| `AudioEngine.Processing.DSPCoreFloat.cpp` | ❌ 同一係数を持つ独自の `inline double fastTanh(double x)` を複製 |
| `AudioEngine.Processing.DSPCoreIO.cpp` | ❌ 同一係数を持つ独自の `inline double fastTanh(double x)` を複製 |

3箇所の係数値は現時点では完全に一致しており、**今すぐ音が変わる不具合ではありません**。しかし将来 `SoftClipPadéPolicy` の係数をチューニングした場合（ヘッダー自身のコメントが「将来の独立チューニングに備える」と明言している想定シナリオ）、`DSPCoreFloat.cpp` と `DSPCoreIO.cpp` の複製版だけが追従せず、**Float入出力経路とDouble入出力経路でサチュレーションカーブが無音のうちに乖離する**、という保守上のリスクを抱えています。これは以前確認された「AVX2分岐とスカラー分岐の動作乖離」と同じ根本原因（重複実装によるドリフト）の別事例です。

さらに、`AudioEngine.h` で宣言され `DSPCoreIO.cpp` で定義されている公開静的メンバ関数 `AudioEngine::DSPCore::musicalSoftClip()` は、コードベース全体を検索してもどこからも呼び出されていません（実際の処理は各ファイルのファイルローカルな `musicalSoftClipScalar()` が直接呼ばれています）。これは孤立した未使用の公開APIです。

**修正**: `DSPCoreFloat.cpp` / `DSPCoreIO.cpp` の独自 `fastTanh()` を削除し、`#include "dsp/math/FastTanhApprox.h"` を追加した上で `convo::dsp::fastTanh<convo::dsp::SoftClipPadeApproxPolicy>(...)` を呼ぶよう統一しました（バグDのリネームと合わせて実施）。`musicalSoftClip()` の未使用公開APIについては、削除するか実際に結線するかはインターフェース設計判断のため、今回はパッチに含めず本文での指摘に留めています。

### バグD【低〜中】識別子への非ASCII文字混入 `SoftClipPadéPolicy`

`FastTanhApprox.h` の構造体名および `DSPCoreDouble.cpp` 内の2箇所の使用箇所で、識別子に **U+00E9（'é'、UTF-8: `C3 A9`）が文字どおり埋め込まれています**（元アップロードファイル `ConvoPeq.md` の該当バイト列を直接検証し、抽出処理側の問題でないことを確認済み）。

`CMakeLists.txt` を確認したところ、MSVC・Intel ICX双方に `/utf-8` フラグが一貫して設定されているため、**現状ビルドが壊れることはありません**。しかし実際に cppcheck の構文解析器はこの文字で完全にクラッシュし（`syntaxError: unhandled character(s) (character code=195)`）、`DSPCoreDouble.cpp` の該当関数（サチュレーション処理そのもの）がcppcheckの解析対象から丸ごと外れていました。これはツール互換性上の実害が既に起きている実例であり、クロスコンパイラ（MSVC/ICX）環境かつ将来 clang-tidy 等の追加導入もあり得るプロジェクトでは、識別子はASCIIのみに保つことを推奨します。

**修正**: `SoftClipPadéPolicy` → `SoftClipPadeApproxPolicy` にリネーム（定義1箇所+使用2箇所、バグCのパッチに統合）。

### バグE【低〜中】入力側DCブロッカーのNaN/Infスクラブが出力側と非対称

`AudioEngine.Processing.DSPCoreIO.cpp` を確認したところ：

- **入力側**（`processInputFloat`相当・`processInputDouble`、DCブロッカー呼び出しは各220行台・280行台）: `sanitizeFiniteChunk()` によるNaN/Infスクラブは DCブロッカー処理の**前**にのみ存在し、**後**には存在しません。
- **出力側**（DCブロッカー呼び出しは375行付近）: DCブロッカー処理の**後**に、AVX2＋スカラーフォールバックによる完全なNaN/Infスクラブ（379–414行）が存在します。

前回セッションでは「Double I/OパスでDCブロッカー後のNaN/Infスクラブが欠如」と一括して報告されていましたが、今回精査した結果、**出力側は既に保護済みで、入力側の2関数のみ未保護**という、より正確な状況であることを確認しました。DCブロッカー自身の内部状態が万一破綻した場合（設計上想定されていない極端な入力等）、入力側ではNaN/Infがそのまま下流のEQ/コンボルバー処理へ伝播しうる非対称性が残っています。

**修正**: 入力側2関数それぞれのDCブロッカー呼び出し直後に、既存の（RTセーフ・AVX2実装済みの）`sanitizeFiniteChunk()` 呼び出しを追加しました。新規コードの追加ではなく既存の実証済みユーティリティの再利用のため、リスクは最小限です。

### バグF【低】ユニットテストの矛盾条件によりテストが実質何も検証していない

`EQProcessorMaxGainTests.cpp::testLog1pUpperBoundStability()` の「極端に小さいdelta」サブテストにおいて：

```
for (double delta = 1e-15; delta < 1e-6; delta *= 10.0)
{
    if (delta > 1e-6)  // 微小項切り捨て条件と同じ
        logBound += std::log1p(delta);
}
```

外側forループの継続条件 `delta < 1e-6` と、内側ifの条件 `delta > 1e-6` は**同時に真になり得ません**（cppcheck: oppositeInnerCondition、到達不能コード）。結果として `logBound` は常に0.0のまま変化せず、テストが実際に検証していたのは `std::isfinite(0.0)` という自明命題のみで、**意図されていたはずの「極小deltaに対するlog1p累積の数値安定性」は一度も検証されていませんでした。**

**修正**: 矛盾する内側if条件を削除し、ループ範囲内の全deltaで無条件に累積するよう修正しました。これによりテストは本来の意図通り、1e-15〜1e-6の範囲でlog1pを繰り返し累積した結果が有限に収まることを実際に検証します。

### バグG【低・移植性】strict-aliasing違反となるポインタキャスト

`CacheManager.cpp` 267行目、mmap経由で読み込んだ `const uint8_t*` を `reinterpret_cast<const double*>` で読み替えてから `memcpy` の読み出し元として使用していました（cppcheck: invalidPointerCast）。x86-64・MSVC/ICXでは実務上問題を起こしませんが、規格上のstrict-aliasing違反パターンです。

**修正**: `double*` へのキャストを経由せず、バイトオフセット計算 + `memcpy` のみで完結するよう変更しました（`memcpy` はバイト列として扱うため、型パニングの懸念がありません）。

## 4. 前回セッションから修正済みと確認した項目
