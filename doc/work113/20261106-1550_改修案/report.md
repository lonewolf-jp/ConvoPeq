## 1. 判定の確定

### 1.1 #12 未監査の内部状態 — バグではない（1 件の堅牢化候補）

| 対象 | 確認結果 |
|---|---|
| SimplePeakLimiter | 状態は `envelope` のみ。更新は `desiredGain < envelope` のときだけで、NaN 比較は false になり保持しない（`SimplePeakLimiter.h:72-76`） |
| 最終段の NaN スクラブ | TruePeak とリミッターの前段で非有限値を 0 にする（`DSPCoreDouble.cpp:692-695`） |
| TruePeakDetector | 入力の非有限値を自前では弾かない。履歴に NaN が入ると FIR 出力が NaN になり、`scanPeak` の比較で無視されて検出値が 0 に落ちる。履歴から流れ出るまで検出不能になるが、`peakHold` は有限のまま（`TruePeakDetector.cpp:96-136`） |
| FixedDelay | `configureFixedLatencySamples` が write pos を戻し、バッファをクリアする（`AudioEngine.h:803-827`）。NaN は遅延して通過するが、状態として固定されない |
| 浮動小数点環境 | `ensureThreadFloatingPointEnvironment` は `thread_local` のフラグで、スレッドごとに 1 回（`AudioEngine.Mmcss.cpp:301-305`） |

結論: 本番チェーンでは NaN はスクラブで除去されるため、#12 はバグではない。TruePeakDetector を直接呼ぶ将来の経路に備え、入力の非有限値ガードを追加するのが望ましい（Info、任意）。

以上で確定する。本番経路に限れば問題ない。ただし、TruePeakDetector を直接呼ぶ経路が将来追加された場合は、入力の非有限値が履歴に入り、検出値が一時的に 0 に落ちるため、呼び出し側か検出器のどちらかでガードを持つべきである。

### 1.2 N1 Bypass テール切断 — 挙動は確認、コードのバグではなく仕様・改善要望

コードの挙動を確認した。

- `ConvolverProcessor::setBypass` は `pendingOverride.bypassed` を更新するだけで、クロスフェードを開始しない（`StateAndUI.cpp:880-900`）。
- RT 側は `runtimeSnapshot.bypassed` が真なら `processBypassWithLatencyCompensation` に切り替え、遅延させたドライ信号を出力する（`Runtime.cpp:305-307,133-200`）。ウェットの畳み込みは実行しない。
- したがって、バイパス時にテールは即座に切れる。フェードはない。切断は即時だ。ウェットの状態は凍結され、解除時に凍結点から再開する。凍結されたテイルの続きが解除の瞬間に現れる可能性があり、操作によっては不自然な残響として聞こえる。

判定: 「テールが切れる」という挙動は事実。ただし、バイパスは通常ドライへ切り替える操作であり、テール保持は仕様として要求されていない。コードの誤りではなく、**ノークリックのバイパスやテール保持を求める場合は機能追加**として扱う。N1 は未判定から「非バグ（仕様）／改善要望」へ確定する。

## 2. 未修正バグの改修案

### 2.1 #4 バンドセッターの入力検証

| 項目 | 内容 |
|---|---|
| 対象 | `EQProcessor::setBandFrequency` / `setBandGain` / `setBandQ`（`EQProcessor.Parameters.cpp:19-74`） |
| 方針 | 値の先頭で `convo::numeric_policy::isFinite` を確認し、非有限なら現状維持。有限値は静的範囲へクランプする（freq 20〜20000、gain ±48 dB、Q 0.01〜20） |

| 優先度 | P1。修正量が小さく、破損セッションの入口を塞げる |
