## 1. 到達できない理由（再掲）

| 分岐 | 到達を妨げているもの | 案 1 で到達できるか |
| --- | --- | --- |
| サイズ超過 | 8 MiB を超える `ValueTree` を実アプリで作れない | **不可**（状態を大きくする手段が別途必要） |
| 書込み失敗 | 読み取り専用ターゲットではネイティブダイアログが上書きを拒否して空の結果を返す。書込み不可ディレクトリではダイアログ自体が保存を拒否する | **可**（保存先だけを注入し、書込みは本物を通す） |
| 生成失敗 | `createXml()` を失敗させる入力が無い | **不可** |

理由は単純である。どれも「外から状態を作れない」ことに尽きる。案 1 が解くのは「ダイアログが邪魔をする」
という 1 点だけであり、状態そのものを作る問題は残る。

保存経路は GUI 専用で、CLI スイッチ 44 種に保存系は無い（`src/MainWindow.cpp` を全走査）。
したがって UI を操作する以外にこの分岐へ到達する方法が無く、既存のテスト手段では検証できない。

## 2. 提案するフック（案）

**案 1: 保存先の注入（推奨）** — ダイアログだけを迂回し、保存処理は本物を通す。

```cpp
// テスト専用（既定では無効）
#if CONVOPEQ_ENABLE_PRESET_SAVE_TEST_HOOK
    if (const auto path = juce::SystemStats::getEnvironmentVariable ("CONVOPEQ_TEST_PRESET_SAVE_PATH", {});
        path.isNotEmpty())
    {
        juce::File target (path);
        // 以降は Save ボタンと同じ処理（サイズ判定 → writeTo → 通知）
    }
#endif
```

この案の利点は、**判定・書込み・通知・既存ファイル保護のすべてが本物の経路を通る**ことである。
読み取り専用のファイルを保存先に指定すれば、`writeTo` が実際に失敗し、通知とファイル不変の両方を確認できる。

**案 2: 分岐の強制** — 保存分岐の先頭で該当分岐へ遷移させる（`size` / `write` / `create`）。
3 分岐を個別に確認できるが、`write` は「書込みを試みずに失敗させる」ため、既存ファイル保護の検証にはならない。

```cpp
// テスト専用（既定では無効）
#if CONVOPEQ_ENABLE_PRESET_SAVE_TEST_HOOK
    if (const auto mode = juce::SystemStats::getEnvironmentVariable ("CONVOPEQ_TEST_PRESET_SAVE", {});
        mode.isNotEmpty())
    {
        if (mode == "size")   { notifySaveFailure ("test hook: size");   return; }
        if (mode == "write")  { notifySaveFailure ("test hook: write");  return; }
        if (mode == "create") { notifySaveFailure ("test hook: create"); return; }
    }
#endif
```

- 追加箇所: `src/MainWindow.cpp` の保存分岐のみ（1 箇所）。
- 有効化条件: コンパイル定義 `CONVOPEQ_ENABLE_PRESET_SAVE_TEST_HOOK` かつ環境変数が設定されているとき。
- 取得する値: 通知ウィンドウの有無と本文、ログ行、保存先ファイルのハッシュ。
- 通常動作への影響: 製品ビルドでは `#if` により**コード自体が存在しない**。
  テストビルドでも環境変数が未設定なら分岐しない。
- 撤去手順: 環境変数を削除し、コミット前に `#if` ブロックを削除する（フックは常用しない）。
- 製品動作に残らないことの確認: リリースビルドの exe に `CONVOPEQ_TEST_PRESET_SAVE` の文字列が
  含まれないことを `findstr` で確認する。

## 3. 代替案（フックを使わない）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | 保存判断を関数へ切り出し（`MainWindow::savePresetToFile(const File&, const ValueTree&)`）、単体テストで 3 分岐を検証 | 変更が「保存分岐の切り出し」に広がる。UI 通知は依然として未検証 |
| B | 判定だけを純関数として公開し、通知はコードレビューで担保 | 既に `isXmlTextWithinLimit()` がその役割。追加変更なし |
| C | 現状のまま（境界＝X-7、通知＝コードレビュー、保護＝JUCE 実装＋BUG-3 の実測） | 追加変更ゼロ。UI 境界は未実測のまま |
| D | **GUI 自動化（UIAutomation）で Save ボタンから保存する** | **追加変更ゼロで実施済み**。正常保存の実測はこれで行った（6,364 B）。読み取り専用ターゲットではダイアログが空を返すため、書込み失敗分岐には届かない |

代替の結論: 既存手段（案 D）で正常保存は確認済み。書込み失敗分岐と既存ファイル保護の**同時確認**だけが
案 1 を必要とする。サイズ超過と生成失敗は、どの案でも実アプリでは作れない（判定は X-7、生成はコードレビュー）。

推奨は **C**（追加変更なし）とする。追加変更はゼロで済む。
UI 境界の実測がどうしても必要な場合に限り、§2 のフックを承認してほしい。
現状でも通知の実装は 1 箇所に集約されており、3 分岐の違いはログに残す文言だけであって、
利用者に見える画面はどれも同じ文面になるため、分岐ごとに表示を確かめる必要性は低いと考える。
