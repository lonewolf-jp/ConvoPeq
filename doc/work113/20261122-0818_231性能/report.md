# #231 の性能測定（decimate 段・4 タップを含む・N=25）

Issue #231 の受入条件のうち、未達だった性能測定をやり直した記録である。前回の報告（`doc/work113/20261122-0526_231検証/report.md`）はカーネルを 1 回だけ測り、中央値も IQR も取っていなかった。今回は 4 タップの構成を含め、25 回の反復から中央値と IQR を出した。結論を先に書く。4 タップでは AVX2 の利点が出ない。32 タップ以上で 2〜3 倍になる。

## 1. 対象と環境

- ソース: `main` `20b7a40e`。対象は `src/CustomInputOversampler.cpp` の decimate 段。
- OS: Windows 11 Home、ビルド 26300
- CPU: 11th Gen Intel Core i7-11700K（8 コア、16 スレッド、3.60 GHz、最大 3.60 GHz）
- MSVC: 14.52.37025
- icx: 2026.2
- 測定は単一スレッド。周波数固定とスレッド隔離はしていない。

## 2. 方法

### 2.1 測ったコード

`src/CustomInputOversampler.cpp` から、decimate 段の内側ループをそのまま抜き出した。

| 対象 | 抜き出した範囲 | 内容 |
| --- | --- | --- |
| `loadStride2` | 45-58 行 | stride 2 の 4 要素ロード |
| `dotProductDecimateAvx2` | 216-287 行 | `convCount >= 8` の 8 重アンロール FMA |
| 4〜7 の簡易 AVX2 | 674-696 行 | `convCount` 4〜7 の分岐 |
| スカラー経路 | 700-702 行 | `convCount < 4` と同じ式 |

外側の n ループは、`base` を 2 ずつ進めて 1 回の出力を計算する形にした。center tap の積和と不正値の検査は、どちらの経路でも同じ 1 命令ずつなので入れていない。比較する差には効かない。

### 2.2 構成

| 条件 | 内容 |
| --- | --- |
| `convCount` | 4、16、32、64 |
| 対応するタップ数 | 7〜9、31、63、127（`convCount = (taps - convParity + 1) / 2`、344 行） |
| 出力サンプル | 1 回の反復で 100 万 |
| 反復 | 各条件 25 回 |
| 計時 | `QueryPerformanceCounter`。反復ごとに開始と終了を取る |
| 中央値 | 25 個の中央値 |
| IQR | 4 分位（inclusive）の差 |

4 タップは `convCount = 4`、つまり `decimateStage` の 4〜7 分岐と解釈した。`taps` が 7 または 9 のときにこの値になる（344 行）。前回の測定は 31・63・127 の 3 条件で、この分岐は含んでいなかった。

### 2.3 ビルド

| 系統 | ビルド | 経路の確認 |
| --- | --- | --- |
| MSVC AVX2 | `cl /O2 /Ob2 /arch:AVX2` | 実行時に `path=avx2`。`.obj` に vfmadd 11、ymm 128 |
| MSVC スカラー | `cl /O2 /Ob2 /arch:SSE2` | 実行時に `path=scalar`。`.obj` に vfmadd 0、ymm 0 |
| icx AVX2 | `icx-cl /O2 /Ob2 /QxCORE-AVX2` | `.obj` に vfmadd 33、ymm 327 |

3 系統とも、全条件で合計値が一致した（`sink=63594.268580`）。数値の一致は確認済みである。

### 2.4 48 kHz → 44.1 kHz について

受入条件は「48 kHz → 44.1 kHz 相当の構成を含む」としている。しかしこのクラスは、レート比を 1、2、4、8 にしか丸めない（`sanitizeRatio`、33-39 行）。48 kHz から 44.1 kHz は 160/147 で、この集合に入らない。したがって「相当する構成」はこのクラスでは作れない。

代わりに、2 倍の decimate（48 kHz 入力 → 24 kHz 出力に相当）で 100 万入力サンプルあたりの時間を出した。1 出力あたりの時間の半分である。この読み替えは本報告の判断であり、受入条件の文言とは一致しない。

## 3. 結果

100 万出力サンプルあたりの時間（ミリ秒）と IQR。

| `convCount` | タップ数 | MSVC AVX2 | IQR | MSVC スカラー | IQR | icx AVX2 | IQR | スカラー比 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 7〜9 | 2.42 | 2.6% | 2.48 | 1.6% | 2.69 | 4.9% | 1.02 倍 |
| 16 | 31 | 6.93 | 5.1% | 7.43 | 2.8% | 5.71 | 3.5% | 1.07 倍 |
| 32 | 63 | 8.06 | 3.0% | 15.88 | 1.5% | 7.87 | 2.1% | 1.97 倍 |
| 64 | 127 | 12.22 | 1.4% | 36.97 | 1.1% | 11.70 | 1.9% | 3.03 倍 |

- IQR / 中央値はすべて 5.1% 以内で、再現性の基準（30%）を満たす。
- 出力 1 サンプルあたりでは、2.42、6.93、8.06、12.22 ns である。
- 2 倍 decimate の 100 万入力サンプルあたりでは、1.21、3.46、4.03、6.11 ms である。
- icx は 16 タップ以上で MSVC の手書き AVX2 より速い（0.82〜0.98 倍の時間）。icx は同じ intrinsics でも命令の並べ方が変わるためである。ただし今回の比較は「手書き AVX2 同士」であり、icx の自動ベクトル化との比較ではない。

## 4. 読み取れること

- 4 タップでは AVX2 の利点が出ない（1.02 倍）。1 出力あたりの履歴参照が 8 要素しかなく、100 万出力で履歴 16 MB を読み流すため、帯域で頭打ちになる。演算の削減より読み出しのコストが大きい。
- 32 タップで約 2 倍、64 タップで約 3 倍になる。前回の 1 回計測（1.68〜3.57 倍）と同じ傾向である。
- したがって C-27 の修正（MSVC で AVX2/FMA 経路を有効にする）は、32 タップ以上の段で効く。4 タップの段では効果が見込めない。
- この結果は、性能改善を「すべての段で速くなる」とは主張しない。段のタップ数に依存する。

## 6. 留保

- 測ったのは decimate 段の内側ループであり、オーバーサンプラ全体ではない。center tap と不正値の検査は除いている。
- 48 kHz → 44.1 kHz はこのクラスで構成できない。2 倍 decimate で読み替えた（§2.4）。
- 単一機種、単一スレッド。周波数固定もスレッド隔離もしていない。
- 履歴は 100 万出力分を毎回読み直すため、実際のブロック処理より帯域の影響が大きく出る可能性がある。4 タップの結果はその影響を受けやすい。
- icx の比較は参考である。MSVC の判断には使わない。

## 7. 再現手順

1. `bench.cpp` を `cl /O2 /Ob2 /arch:AVX2` と `/arch:SSE2` でビルドする。icx は `icx-cl /O2 /Ob2 /QxCORE-AVX2`。
2. 各実行ファイルを `bench.exe 1000000 25 <csv> <variant>` で走らせる。
3. CSV から条件ごとの中央値と IQR を計算する。
4. ビルドと実行は `run.cmd` にまとめた。

成果物は同じフォルダに置いた。

- `bench.cpp` — 測定用のソース（製品コードではない）
- `run.cmd` — ビルドと実行
- `bench_avx2.csv`、`bench_scalar.csv`、`bench_icx.csv` — 25 回 × 4 条件の生データ
