# ポリフェーズ利得の仕様選択資料（#3）

- 作成: 2026-11-06
- 対象: `ConvoPeq 構造・妥当性検証レポート` の #3（ポリフェーズ利得誤差）
- 目的: 既定 ON、decimate 側の補償、現状維持の 3 方式を比較し、Owner が仕様を選べる材料を整理する
- 制約: 本資料は調査のみ。production コード、既定値、テスト期待値、CMake、CI は変更していない

## 0. 決定（2026-11-06）

Owner は方式 **C（現状維持）** を選択した。

- 現行の利得規約（0.75^n）と音響動作を維持する。
- 方式 A・B の実装は未承認。既存プロジェクトの音量、SoftClip、OS ドメイン振幅、テスト契約に関する追加判断が必要なため。
- Phase 0 テスト契約は改訂しない。音響仕様も変更しない。
- リリースは #1 の修正を対象とする保守的なものとし、#3 は含めない。

## 1. 現行の利得規約

### 1.1 実装

`CustomInputOversampler.cpp` の各段は、次の規約で動く。

| 箇所 | 内容 |
|---|---|
| `prepareStage` | 半帯域 FIR を合計 1 に正規化し、中心タップを 0.5 に固定する |
| `interpolateStage` | 畳み込み側は常に `*= 2.0`。中心側の `*= 2.0` は `#if CONVOPEQ_CORRECT_POLYPHASE_GAIN` 内のみ |
| `decimateStage` | 2 倍も補償もない。畳み込みと間引きのみ |
| 既定 | `CONVOPEQ_CORRECT_POLYPHASE_GAIN` は OFF（`CMakeLists.txt:134`、`build/CMakeCache.txt` も OFF） |

### 1.2 解析

DC 入力に対する 1 段のラウンドトリップ利得は 0.75 になる。中心タップが 0.5 のまま、畳み込み側だけ 2 倍されるためである。

| 段数 | DC 利得 | dB |
|---|---|---|
| ×2（1 段） | 0.750000 | −2.498 |
| ×4（2 段） | 0.562500 | −4.997 |
| ×8（3 段） | 0.421875 | −7.495 |

### 1.3 実測

`build/Release/PolyphaseGainFidelityTests.exe` の実行結果（PASS=54、FAIL=0）で、`dcBase` が 0.75／0.5625／0.421875、`dcCand` が 1.0、`production_flag` が undefined/off であることを確認した。テスト自身が「Shadow fidelity gate であり production 正しさの gate ではない」と明記している。

### 1.4 本番経路

`AudioEngine.Processing.DSPCoreDouble.cpp` の `processUp`（`:354`）から `processDown`（`:534`）の間に、段数分の補償はない。あるのはユーザー設定の `outputMakeupGain`（既定 +12 dB、`AudioEngine.h:2796`）とコンボルバ入力トリムのみである。SoftClip 有効かつ OS=1 のときは、局所 2 倍 OS（`:496-507`）を通るため同じ損失が乗る。

## 2. 3 方式の比較

### 2.1 方式 A: 利得補正を既定 ON にする

`CONVOPEQ_CORRECT_POLYPHASE_GAIN=ON` とし、中心タップも 2 倍する。

| 観点 | 内容 |
|---|---|
| 出力レベル | OS 有効時に +2.50／+5.00／+7.50 dB（×2／×4／×8）。DC ラウンドトリップが 1.0 になる |
| OS ドメインのレベル | 現行より 2.5〜7.5 dB 高い。SoftClip とリミッターには設計どおりの振幅で入る |
| SoftClip | 同じ閾値でも早く掛かり始める。歪み量が増える方向 |
| リミッター | 入力が上がるためゲインリダクションが増える。閾値は 0.8414（−1.5 dBFS）、ニーは 0.1087 |
| AGC | 出力レベルが上がるため、AGC の目標へ向けた追従がやり直しになる。時定数は attack 0.2 秒、release 2.0 秒 |
| 既存プロジェクト | OS を有効にしているセッションは音量が上がる。ミックスバランスとクリップ余裕が変わる |
| プリセット再現性 | パラメータ値は変わらないが、同じ設定で鳴る音量が変わる |
| テスト契約 | `PolyphaseGainFidelityTests` は 0.75 を base として期待し、production flag の定義を契約違反として扱う。期待値の更新と Phase 0 契約の改訂が必要 |
| 実装量 | マクロ 1 つの既定変更が中心。ただしテスト側の更新が大きい |
| リスク | 音作りと既存曲の再現性に直接触れる。中〜高 |

### 2.2 方式 B: decimate 側で補償する

間引きの直前または直後に、段数分の `1/0.75 = 1.3333` を乗算する。

| 観点 | 内容 |
|---|---|
| 出力レベル | DC ラウンドトリップが 1.0 になる。レベル変化は方式 A と同じ |
| OS ドメインのレベル | 現行のまま（低い）。SoftClip とリミッターの掛かり方は現行と変わらない |
| SoftClip・リミッター | OS ドメインの振幅が変わらないため、歪みとリダクションの挙動は現行維持。出力段のクランプだけが持ち上がる |
| AGC | 出力が上がるため追従はやり直しになる。ただし OS ドメインの非線形処理は現行と同じ |
| 既存プロジェクト | 音量は A と同じだけ上がる。ミックスバランスへの影響は A と同等 |
| テスト契約 | Shadow 参照との bitwise 比較が decimate の補償で崩れる。新しい参照モデルか、補償込みの期待値が必要。production flag は OFF のままにできる |
| 実装量 | decimate に 1 乗算を足す。RT 安全性は保たれる（確保もロックも増えない） |
| リスク | 「補償の位置」が音響仕様になる。SoftClip の掛かり方を変えずにレベルだけ直せるが、その分だけ現行の OS ドメイン設計を追認する形になる |

### 2.3 方式 C: 現状維持

| 観点 | 内容 |
|---|---|
| 出力レベル | OS 有効時に 2.5〜7.5 dB 低いまま |
| 音作り | 現行の音と既存曲の再現性を完全に維持する |
| SoftClip・リミッター | 現行どおり。レベルが低い分だけ余裕がある |
| 既存プロジェクト | 影響なし |
| テスト契約 | 変更不要 |
| 残る問題 | 「OS を入れるとレベルが下がる」という仕様が残る。ユーザーはメイクアップで補う必要がある。将来の修正時に移行が必要 |
| リスク | 仕様としての一貫性は低い。低 |

## 3. 比較表

| 項目 | A 既定 ON | B decimate 補償 | C 現状維持 |
|---|---|---|---|
| DC ラウンドトリップ | 1.0 | 1.0 | 0.75^n |
| OS 有効時の出力変化 | +2.5〜+7.5 dB | +2.5〜+7.5 dB | なし |
| OS ドメインの振幅 | 現行より高い | 現行のまま | 現行のまま |

| リミッターのリダクション | 増える | 出力段のみ増える | 変わらない |

| 主なリスク | 既存曲の音量と音作り | 補償位置の仕様化 | 仕様の不整合が残る |

## 4. 方式ごとに決めるべきこと

### A を選ぶ場合

- 既存プロジェクトの音量変化（最大 +7.5 dB）を許容するか
- 出力メイクアップ既定 +12 dB との関係をどう扱うか
- SoftClip の掛かり方が変わることを仕様として認めるか
- Phase 0 契約テストの期待値を更新してよいか

### B を選ぶ場合

- 補償を間引きの前後どちらに置くか（線形なので DC は同じ。フィルター後の飽和には差が出ない）
- OS ドメインの振幅を現行のまま据え置くことを仕様として認めるか
- Shadow 参照モデルをどう更新するか

### C を選ぶ場合

- 「OS 有効時はレベルが下がる」を仕様として明記するか
- 将来修正するときの互換性の方針（メジャー更新で変更する等）を決めるか

## 5. テストへの影響

| 方式 | 既存テスト | 追加が必要なテスト |
|---|---|---|
| A | `PolyphaseGainFidelityTests` の base 期待値と production flag 契約の更新 | DC 利得 1.0、全段数、全 SR、SoftClip とリミッターの挙動 |
| B | Shadow 参照との bitwise 比較の更新 | decimate 補償の DC 利得、周波数応答、既存曲の差分 |
| C | 変更なし | なし（現行契約の維持） |

## 6. Owner が決める事項

1. 利得規約の契約: DC ラウンドトリップを 1.0 とするか、現行の 0.75^n を仕様とするか
2. 方式: A、B、C のいずれか
3. 既存プロジェクトの音量変化を許容する範囲
4. テスト契約の改訂を承認するか
5. 変更をどのリリース種別（パッチ／マイナー／メジャー）に載せるか

## 7. 本資料の位置づけ

本資料は比較材料であり、#3 の修正承認ではない。production flag は OFF のまま、コードとテストは変更していない。
