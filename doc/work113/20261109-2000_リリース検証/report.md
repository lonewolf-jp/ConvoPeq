## §1 目的と範囲

Polyphase gain correction（E）と、Bypass の IR 保持（F）・テール幾何（H）・倍率上限（I）について、**実際の出力音声を WAV に記録し、数値分析で確認する**。既存の実装・テスト・測定結果は基礎資料として参照するが、本検証の結論は本測定の結果に基づく。

対象外（本検証では扱わない）:
- 人による聴感評価（Owner 指示により実施しない）
- リリース承認そのもの（本報告は承認と同一視しない）
- 音質の優劣の断定（数値からは導かない）

- True Peak（正弦、IIR）: ON −5.815 / −5.992 / −6.004 dBTP、OFF −8.313 / −10.990 / −13.500 dBTP。差は **+2.499 / +4.998 / +7.496 dB**

- ON−OFF 差の周波数依存: 成分ごとの差は 6 構成すべてで 0.0002 dB 以内（8× IIR の 3 kHz +7.4964、10 kHz +7.4965、他は +7.4963）。帯域内では平坦な利得差

### 3.3 NUC の IR・tail・Bypass・ブロック長（F/H/I）

IR 1.0 s、インパルス入力。誤差は float32 WAV の量子化を含む。

| 条件 | IR との最大誤差 | 固定区間（0.5〜1.0 s）の絶対エネルギー | IR との差 |
|---|---|---|---|
| tailMode=2（Bypass）block 256 | 1.49e-8 | −1.976 dB | 0.000 dB |
| tailMode=2 block 512 | 1.49e-8 | −1.976 dB | 0.000 dB |
| tailMode=2 block 1024 | 1.49e-8 | −1.976 dB | 0.000 dB |
| tailMode=1 block 256 | 1.093e-1（末尾マーカー部） | +1.176 dB | +3.152 dB |
| tailMode=1 block 512 | 1.093e-1 | +1.176 dB | +3.152 dB |
| tailMode=1 block 1024 | 1.093e-1 | +1.176 dB | +3.152 dB |

- 固定区間の絶対エネルギーは Part 8 の Production テストと同じ定義（0.5〜1.0 s の 10 log10 Σx²）で、tailMode=1 の **+1.176 dB** は同テストの基準値（H-1）と一致する。IR 単体は −1.976 dB であり、差の **+3.152 dB** がテール整形分にあたる。ブロック長による差は 0.001 dB 未満
- Bypass の IR との差 1.49e-8 は float32 の**量子化床**に由来する。最大誤差は振幅 0.290169 のサンプルで、同値の float32 ULP 2.98e-8 の**ちょうど 0.50 ULP**（最近接丸めの上限）。1e-7 を超えるサンプルは 0 件
- 二重精度の Production テスト（`TailLayerIntegrityTests`）では最大 3.9e-16。本測定の 1.49e-8 は測定系（float32 WAV）の精度上限であり、実装の一致精度は二重精度側で評価する
- Bypass のブロック長間: IR 区間内で差があるのは 2 サンプルのみ、IR 終端以降の無音部に 2,162 サンプル（最大 9.7e-17）。信号区間は実質ビット一致で、差は無音部の表現限界にとどまる
- tailMode=1 はテール層で固定区間を持ち上げ（IR 比 +3.152 dB、絶対値 +1.176 dB）、そのエネルギーはブロック長に依存しない
- tailMode=1 のブロック長間の差: 最大 0.0962。差があるのは [5888, 6143] の 256 サンプル（L0/L1 の境界直前）に限られ、それ以外は最大 3.3e-17（無音部の表現限界）
- tailMode=1 の IR 全体 RMS は −19.46〜−19.51 dB（IR は −20.28 dB）。末尾マーカー部の差 0.109 は整形によるもの

### 3.4 リミッター

- 本検証のレンダラは OS / NUC のコンポーネントであり、エンジン後段のリミッターを含まない。エンジン全体を WAV に記録する既存経路が無いため、**測定を実施していない**（Inconclusive）

### 3.5 追加観測（V-6・受入基準の対象外）

インパルス応答で ON−OFF を単一スカラー倍で近似したときの残差は、ピークに対して 2× IIR −55.0 dB、8× IIR −56.2 dB、2× LP −60.4 dB、8× LP −61.6 dB だった。8× LP のプリリンギング領域では ON/OFF 比が 1.7778（= 0.75⁻²）で、主応答と定常トーンでの 2.3704（= 0.75⁻³）と異なる。

- つまり「差は純利得」は**定常トーン（V-1/V-2/V-3 の信号）に対する結論**であり、インパルス過渡の −55 dB 以下の形状差は別に存在する
- この形状差が既存指標の窓内 argmax の移動（§4 の LP3 r8）に関与し得るが、因果は確定していない
- 既存指標の遅延（ON / OFF）は r2 255/255、r4 286/287、r8 290/290、LP r2 501/501、LP r8 461/475。窓内 argmax は近接サンプル間で 1 サンプル動く例がある（r4 IIR）

### 5.2 英文（README / Release Notes 用・最終）

> **Oversampling gain correction is now enabled by default.**
>
> The input oversampler now has unity round-trip gain at 2×, 4× and 8× oversampling. Earlier builds attenuated the signal by 2.50, 5.00 and 7.50 dB at those factors (measured: 2.4988, 4.9975 and 7.4963 dB; 48 kHz, −6 dBFS tone, offline component render). Existing sessions therefore play louder with unchanged settings. The measured increase is about 2.5 dB at 2×, 5.0 dB at 4× and 7.5 dB at 8×.
>
> Preset values are not modified. Re-check the output gain and the limiter settings before playback.
>
> `-DCONVOPEQ_CORRECT_POLYPHASE_GAIN=OFF` restores the previous response.
>
> The measurements cover gain, in-band frequency flatness and the convolver's bypass/tail behaviour at 48 kHz. Limiter behaviour, other sample rates, level-dependent behaviour, long-run operation and hardware playback were not measured. No claim is made about improved or degraded sound quality.

### 5.3 和文（リリースノート用・最終）

> **オーバーサンプリングの利得補正を既定で有効にしました。**

- 検証は production のコンポーネント（OS / NUC）を直接リンクしたオフライン描画であり、エンジン全体（EQ・ソフトクリップ・リミッター・ディザ）を通した出力ではない
- WAV は float32 のため誤差の下限は約 1.5e-8（0.5 ULP）。二重精度が必要な一致判定は `TailLayerIntegrityTests`（3.9e-16）が担う
- tailMode=1 のブロック長差は L0/L1 境界の 256 サンプル（0.0962）に限局する。境界位置は L0 長（block 256 で 5,888、512/1024 で 6,144）に依存する。聴感上の影響は評価していない
- インパルス過渡では ON/OFF が単一スカラー倍にならない（残差 −55〜−62 dB、§3.5）。V-3 の結論は定常トーンに対するもの
- 既存 `PolyphaseGainMetrics` の遅延は 1 ブロック 512 サンプル窓の argmax（上限 501）であり、LP r2 は窓端、LP r4/r8 は真のピークが窓外にある。本測定の全長 argmax とは測定量が異なる

## §7 追加実装・変更提案

- 今回の検証結果に基づく追加実装は**不要**（Owner 判断）
- リミッター検証経路の追加、または LP3 r8 遅延差の原因調査で実装変更が必要になった場合は、別途変更提案を提出し、Owner の承認を待つ。承認なしに実装を開始しない
