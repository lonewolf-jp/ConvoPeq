# #1 残存 A（探索上限 64）の保留記録

- 判断日: 2026-11-06
- 対象: 係数キャッシュのキー衝突時に行う再探索の上限（現行 32 回）
- 結論: **保留を維持する。探索上限 64 への変更は承認しない。**

## 1. 現状

キーが衝突した場合、`AudioEngine.Cache.cpp` は探索用のハッシュを進めながら空きスロットを探す。探索は 32 回で打ち切る（`for (int probe = 0; probe < 32; ++probe)` の 2 箇所）。32 回すべて衝突すると、新規キャッシュを確保した後に破棄し、`nullptr` を返す（fail-closed）。

呼び出し側（`AudioEngine.Snapshot.cpp:56-70`）は、キャッシュを取得できない場合にスナップショットを抑制し、`eqCacheSnapshotCreateMissCountNonRt` を加算する。誤った係数は返さず、公開済みスナップショットの一貫性も崩さない。

通常の操作では 32 回の連続衝突は起きない。発生するのは、同一キーを大量に作り出す特殊な条件に限られる。

## 2. 保留の理由

1. 探索上限の変更が必要となる頻度と性能影響が提示されていない。
2. 上限を増やすことは、衝突時の余裕を増やすだけで、衝突の根本原因（キー設計）を解消するとは限らない。
3. 上限の変更には、探索時間とメモリ使用量の再評価が必要である。

## 3. 再審査条件

次の条件が揃った時点で再審査する。

| 条件 | 内容 |
|---|---|
| 発生条件 | 32 回衝突の再現条件を確認する |
| 性能評価 | 現行の 32 と候補の 64 を比較する |
| メモリ評価 | 一時キャッシュの生成頻度と容量を測る |
| 実装案 | 上限 64、探索戦略の変更などを比較する |
| 判断 | 上記を踏まえて Owner が実装方針を決める |
