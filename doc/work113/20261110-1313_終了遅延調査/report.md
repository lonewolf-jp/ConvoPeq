# 調査 B: 終了処理に約 30 秒を要する問題

## §1 実施した調査・測定

### 1.1 測定方法（コード変更なし）

アプリは `[DIAG] ~MainWindow: step N` をログに書く。CLI の `--cli-log-file` を使うとロガーが早期に外れるため、**`--cli-log-file` を付けずに**実行し、実行ファイル隣の `ConvoPeq.log` を 40〜100 ms 周期で読み、行の出現時刻を記録した。併せて以下を測定した。

- プロセスの CPU 時間（`Process.TotalProcessorTime`）と書込みバイト数（`Win32_Process.WriteTransferCount`）の 100 ms サンプル
- `%APPDATA%\ConvoPeq\` の `noise_shaper_learn.xml`・`device_settings.xml`・`learned_state.xml` の更新時刻とサイズ
- 実行ごとの総経過時間

実行条件は `--cli-run --cli-exit-ms 2000`（2 秒動かして終了。1 回だけ 3000）。通常ファイル条件で 6 回測定し、総経過は 25.9〜28.7 秒だった。

### 1.2 測定した 2 条件

同じバイナリ・同じ引数で、**学習ノイズシェイパー状態ファイルの大きさだけ**を変えて比較した。

| 条件 | `noise_shaper_learn.xml` |
|---|---|
| 通常 | 278,331 バイト（180 個の `Bank_` 要素、543 個の `<`、1,264 行、最長行 948 文字） |
| 小 | 38 バイト（`<NoiseShaperLearningData version="2"/>`） |

小ファイルでの測定後、元ファイルはバックアップから復元し、ハッシュ一致を確認した（278,331 バイト）。

### 1.3 既報の値との関係

既報の「`setProcessor(nullptr)` 約 2.1 秒」「`saveSettings` 約 9.8 秒」「`MainWindow` 破棄後の `AudioEngine` 破棄 約 18 秒」のうち、**3 番目は今回の測定と一致しない**。今回の測定では `~AudioEngine` の後始末は 53 ms（26,784 ms → 26,837 ms）である。別実行では 100 ms サンプル内に収まり、それ以上の分解能は取得していない。既報の 18 秒は、`~MainWindow` 完了からプロセス終了までを「エンジン破棄」と見なした推定であり、実際にはその区間に別の処理（後述の起動側の待ち）が含まれていた可能性がある。本報告では実測値のみを扱う。

## §2 直接確認できた事実

### 2.1 タイムライン（通常ファイル、総経過 26,937 ms）

| 時刻 | 事象 | 区間の長さ |
|---|---|---|
| 12,521 ms | `[CLI] Auto-exit scheduled in 2000ms` | 起動に **12.5 秒** |
| 14,354 ms | `Auto-exit flush` → `shutdown() enter` → `D167` → `~MainWindow ENTER` | 実行 1.83 秒 |
| 16,503 ms | `step 5 stopTimer` / `step 6 saveSettings` | ドレイン **2.15 秒** |
| 26,743 ms | `step 7 removeAudioCallback` | **saveSettings 10.24 秒** |
| 26,784 ms | `~MainWindow: complete` | 後続 41 ms |
| 26,837 ms | `~AudioEngine: shutdown sequence complete` | **エンジン破棄 53 ms** |
| 26,928 ms | `mainWindow.reset() completed` | 91 ms |
| 26,937 ms | プロセス終了 | — |

### 2.2 タイムライン（小ファイル、総経過 5,892 ms）

| 時刻 | 事象 | 区間の長さ |
|---|---|---|
| 1,795 ms | `Auto-exit scheduled` | 起動 **1.8 秒** |
| 3,546 ms | `Auto-exit flush` → `~MainWindow ENTER` | 実行 1.75 秒 |
| 5,671 ms | `step 6 saveSettings` | ドレイン **2.12 秒** |

### 2.3 差分

| 区間 | 通常 | 小 | 差 |
|---|---|---|---|
| 起動 | 12.5 秒 | 1.8 秒 | **+10.7 秒** |
| ドレイン（releaseResources） | 2.15 秒 | 2.12 秒 | ほぼ同じ |
| saveSettings | 10.24 秒 | 0.05 秒 | **+10.2 秒** |
| エンジン破棄 | 53 ms | 同程度 | ほぼ同じ |
| 総経過 | 26.937 秒 | 5.892 秒 | **+21.045 秒** |

### 2.4 saveSettings 内部の観測

- saveSettings の窓（16.6〜26.7 秒）で、プロセスの CPU 時間は **+10,391 ms**、書込みは **294,305 バイト**だった。I/O は小さく、CPU もしくは待ちが支配的である。
- `noise_shaper_learn.xml`（278,331 バイト）と `device_settings.xml`（11,728 バイト）の更新時刻は、どちらも窓の**末尾**（25,759 ms／25,761 ms）だった。つまり **9.8 秒はファイル書込みの前**に消費されている。
- 書込み自体は 2 ms 以内に完了している。

## §3 事実から導いた判断

- 「終了に約 30 秒」の実体は、**起動 12.5 秒＋実行 1.8 秒＋終了 12.6 秒**である。終了だけを見ると約 12.6 秒で、そのうち 10.2 秒が `saveSettings`、2.15 秒がドレインである。
- `saveSettings` の 10.2 秒は、**学習ノイズシェイパー状態ファイルの読み込み・再構築**に起因する。同じ処理でファイルを 38 バイトにすると 66 ms になるため、デバイス問い合わせや XML 書込み（2 ms）ではない。
- 起動側も同じファイルの読み込みで **+10.7 秒**かかっている。合計 +20.9 秒がこのファイルに帰属する。
- `~AudioEngine` の後始末とデバイスクローズは 0.1 秒未満であり、既報の「エンジン破棄 18 秒」は本測定では支持されない。
- ドレインの 2.1 秒は両条件で同じであり、ファイルとは無関係の固定コストである。

## §4 未確認事項と制約

- 10 秒を消費している**具体的な関数**は未確定である。候補は `DeviceSettings::saveNoiseShaperState` 内の「既存 XML のパース」と「180 要素（10 サンプルレート × 3 ビット深度 × 6 モード）の再構築」、および `loadNoiseShaperState` のパース。切り分けには計測用の一時コード（または専用ベンチマーク）が必要で、今回はコード変更が許可されていないため実施していない。
- ファイルは 277 KB・543 個の `<` であり、単純な文字走査や XML パースの規模としては小さい。にもかかわらず 10 秒かかるため、**属性数や要素数に対して超線形**な処理（例: 要素ごとの線形探索の入れ子、`NamedValueSet` の線形参照）が疑われるが、断定はできない。
- CPU 時間 +10.4 秒はプロセス全体の値であり、どのスレッドが消費したかは特定できていない（スレッド別の CPU 採取は試みたが、対象スレッドの同定には至らなかった）。
- 実機の音声デバイス（ASIO）を使った実行であり、デバイス初期化の内訳（起動 1.8 秒のうちどこまでがデバイスか）は分離していない。
- 起動側の +10.7 秒は**小ファイル条件 1 回**との比較である（通常ファイル側の起動は 2 回測定で 12.4〜12.5 秒）。再現回数は 1 回であり、断定には追加測定が要る。

## §5 追加変更が必要な場合の提案（未実施・承認待ち）

1. **計測用の一時ログを入れて切り分ける**（最小の追加変更）
   - `saveNoiseShaperState` の冒頭（パース前後）、180 要素（10 サンプルレート × 3 ビット深度 × 6 モード）のループ前後、`createStateXml` の前後、書込み前後に `steady_clock` の経過を出す。計測後に削除する。
   - 影響: なし（計測のみ）。所要 1 ビルド。
2. **読み込み・保存のコストを下げる**
   - 例: 保存時に既存ファイルをパースせず、メモリ上のバンク状態から直接構築する。差分保存にする。XML を圧縮・バイナリ化する。
   - 影響: 保存形式の互換性（B-15 の version 管理と関係）、既存ファイルの移行、テストの更新。
3. **保存を非同期化する**
   - 終了経路から 10 秒の同期保存を外し、保存専用スレッドで書く。終了時は「保存完了を待つ上限」を決める必要がある。
   - 影響: 終了時にデータを失うリスク、待ち時間の設計。
4. **スモークテストのタイムアウトを延ばす**
   - これは症状を隠すだけであり、解決策として先行させない（指示どおり）。

現時点では 1 の計測を推奨する。原因の関数を確定してから 2 か 3 を選ぶべきで、いずれもコード変更の承認が必要である。
