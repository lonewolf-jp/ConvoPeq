## 2. Owner 確認事項への回答

### 2.1 float の符号保持と正規化

`EQProcessor.h:861-871` の `canonicalFloatBits` は次の順で判定する。

| 入力 | 出力 |
|---|---|
| NaN | `0x7FC00000`（符号なし quiet NaN） |
| +0.0 / −0.0 | `0` |
| その他 | ビット列をそのまま返す（符号を含む） |

符号ビットのマスクは行わない。±0 は同じ値なので統一し、NaN は係数がバイパス固定なので単一表現に寄せる。符号付きの通常値はすべて区別される。

確認結果: 妥当。`#1` の直接原因（符号の消失）は解消している。

### 2.2 係数生成時とキー生成時のクランプ規約

キー生成は `EQProcessor.h:873-913`。クランプは `validateAndClampParameters`（`EQProcessor.Coefficients.cpp:91-103`）と同じ式を使う。

| パラメータ | キー | 係数生成 |
|---|---|---|
| frequency | `jlimit(20, min(20000, 0.95·Nyquist))` | 同じ |
| gain | `jlimit(−48, 48)` | 同じ |
| Q | `jlimit(0.01, 20)` | 同じ |
| totalGain | `jlimit(−48, 48)` | セッターで同じ |
| saturation | `jlimit(0, 1)` | セッターで同じ |

サンプルレートが 0 以下のときは周波数クランプを省略する。この場合 `createCoeffCache` は全バンドをバイパス係数にするため、キーが分かれても係数は同じになる。誤ヒットはしない。

確認結果: 妥当。キーと係数の意味は一致している。無効バンドだけは値が係数に反映されないが、キーには残る（§4.2）。

### 2.3 ハッシュ衝突時のキー照合と退避

`AudioEngine.Cache.cpp:59-136`。

1. キーを 1 回だけ作り、基本ハッシュを算出する（`:59-60`）。
2. ロックなしで `find(hash)` し、`cacheKeyMatches` が真なら返す（`:63-76`）。
3. 偽なら `probeCacheHash(hash, probe)` で次のハッシュへ進む（`:78`）。最大 32 回。
4. 空きが見つかったら、そのハッシュでキャッシュを作り、lock 下で再確認する（`:101-136`）。
5. lock 下でもキー不一致なら退避を続け、空きに挿入する。

`probeCacheHash` は基本ハッシュと probe 番号だけで決まる（`EQProcessor.h:950-958`）。同じパラメータの再探索は同じ順序をたどるため、挿入位置に到達できる。

確認結果: 妥当。ハッシュ一致だけでは返さない。

### 2.4 32 回退避上限の fail-closed

`AudioEngine.Cache.cpp:101-140`。32 個の候補がすべて別キーで埋まった場合は、作成したキャッシュを破棄し、`nullptr` を返す（`:138-141`）。呼び出し側の `AudioEngine.Snapshot.cpp:56-58` はハッシュ 0 のままとなり、RT 側は `pinByHash` に失敗して EQ をバイパスする（`AudioEngine.h:4373-4379`）。

誤った係数を返す経路はない。無音方向の失敗であり、安全側である。

確認結果: 妥当。

### 2.5 無効バンドのキー保持による余分なキャッシュ

無効バンドは `createCoeffCache` でバイパス係数になる（`ProcessingCache.cpp:45-55`）。一方、キーは freq/gain/Q を保持するため、無効バンドの値だけを変えると別キーになり、新しいキャッシュが作られる。

| 観点 | 評価 |
|---|---|
| 誤ヒット | なし（キーが違えば別エントリ） |
| メモリ | 値の組み合わせごとに 1 件増える。1 件あたり約 320 バイト |
| RT | 影響なし（参照はハッシュ） |
| 実害 | 通常の操作では無効バンドの値を変えても音は変わらないため、キャッシュが増えるだけ |

確認結果: 既知の非効率として許容できる。必要なら将来、無効バンドの値をキーで固定値に正規化する余地がある。今回は音響仕様を変えないため、そのままにした。

### 2.6 統合レベルの衝突テスト不足

追加した `STG11-D13`（`STG11EQRetireTests.cpp:403-524`）は、キー生成・ハッシュ・照合のプリミティブを検証する。`getOrCreate` の退避ループ全体は `AudioEngine` に依存するため、単体テストの範囲外である。

| 層 | 検証 |
|---|---|
| キーとハッシュ | 16 項目で検証済み |
| 照合プリミティブ | 異なるキーを拒否することを検証済み |
| 退避ループ | コードレビューのみ（`Cache.cpp:63-140`） |
| 統合 | 未検証（AudioEngine の起動が必要） |

確認結果: 不足は事実。統合テストを追加する場合は、`AudioEngine` を起動して同一ハッシュの 2 キーを登録する専用のハーネスが必要になる。今回はスコープ外とした。

## 3. 差分の確認

### 3.1 ヘッダ

- `EQCoeffKey` は POD で、float を持たず canonical bits のみを持つ。`operator==` は既定実装で、NaN の比較問題がない。
- `EQCoeffCache` に `key` を追加した。サイズは約 320 バイト増える。
- キー関数は header-only の inline。単体テストから直接呼べる。
- `<cmath>`、`<cstring>`、`<limits>` を追加した。`<limits>` は未使用の可能性がある（害はない）。

### 3.2 ProcessingCache

- `computeParamsHash` はキー経由に変わった。呼び出しは `AudioEngine.Cache.cpp` と `BassBuzzMeasurement.cpp` のみ。
- `createCoeffCache` はキーとハッシュを保存する。`getOrCreate` が衝突時に `paramsHash` を上書きする。
- 旧 `floatToCanonicalBits` と `hashCombine` の残存参照は 0 件。

### 3.3 Cache

- ヒット時の `resolve` は従来どおり。キー比較を追加した。
- lock 下の再確認は、キー比較と退避を含むループに置き換えた。
- 既存の削除順序（`invalidateHandleBeforeDestroy` → `delete`）は維持した。
- RT 経路（`pinByHash`）は変更していない。RT に確保もロックも追加していない。

### 3.4 テスト

- 16 項目。符号、クランプ、SR、ブロック、各フィールド、照合、決定性を確認する。
- 既存の TD1-0〜TD1-4b も同じ実行ファイルで PASS した。

## 4. 残存する論点

| # | 論点 | 影響 | 対応案 |
|---|---|---|---|
| 1 | 32 回すべて衝突した場合、同一キーの再探索で一時キャッシュを 1 個作る | 性能のみ。誤ヒットはない | 探索開始位置を記録する、または上限を増やす |
| 2 | 無効バンドの値がキーに残る | 余分なキャッシュ | 将来、無効バンドの値を固定値に正規化 |
| 3 | 統合レベルの衝突テストがない | 退避ループはレビューのみ | 専用ハーネスを追加 |
| 4 | `computeParamsHash` の意味がクランプ後へ変わった | 呼び出し 2 箇所。保存形式には使われない | 変更なし |
| 5 | `<limits>` の追加は未使用 | なし | 削除可 |

## 5. 結論

- 符号の消失は解消している。
- キーと係数のクランプ規約は一致している。
- ハッシュ一致だけでは返さず、キー照合と退避を行う。
- 32 回の上限では fail-closed になり、誤った係数は返さない。
- 無効バンドの余分なキャッシュと統合テスト不足は、既知の残存論点として記録した。
