## 1. Finding in one line

**The rate-domain incoherence that the recorded `p1_5` §13.4 anomaly would require
does not exist in the new authority.** Coefficient generation and the audio rate
share one value, `processingRate`, by construction. The `16×` historical defect's
mechanism is also absent: its `sr > 384000` fallback has been removed.

## 2. H-1 — which rate domain interprets the centre frequency

The normalised frequency is formed against whatever `sr` the caller supplies.

```text
src\eqprocessor\EQProcessor.Coefficients.cpp

  L66673   calcPeakingSVF:    const double g  = tan(pi * freq / sr);
  L66634   calcLowShelfSVF:   const double g  = tan(pi * freq / sr) / sqrt(A);
  L66711   calcHighShelfSVF:  const double g  = tan(pi * freq / sr) * sqrt(A);
```

So the domain is set entirely by the argument. Both paths were traced to their
argument.

## 6. H-5 — centre frequency, Q and bandwidth across the OS boundary

```text
  L66673   g = tan(pi * freq / sr)        normalised centre, sr = processingRate
  L66674   k = 1.0 / (q * A)               Q used directly, no rate dependence
  L66634   LowShelf:  g = tan(pi*freq/sr) / sqrt(A)
  L66635   LowShelf:  k = 1.0 / q
  L66711   HighShelf: g = tan(pi*freq/sr) * sqrt(A)
  L66407   Cookbook:  alpha = sin(w0) / (2.0 * q)      w0 = 2*pi*freq/sr
```

`freq/sr` is the normalised centre. As the oversampling factor rises, `sr` rises
proportionally, so the normalised centre falls proportionally, and the filter runs
at the correspondingly higher rate. The band therefore keeps its centre **in Hz**
and its Q-defined shape. `Q` itself carries no rate term and is not rescaled.

**H-5 verdict: centre frequency, Q and bandwidth are OS-coherent. No OS-dependent
re-derivation of the band shape exists in the coefficient functions.**

## 7. H-6 — the 250 Hz / 125 Hz peak-displacement candidate

`p1_5` §4 line 50 recorded, as *consistent with*, the band being processed at the
OS rate with the specified frequency read against the base rate, giving peaks at
250 Hz (os=4) and 125 Hz (os=8).

For that to hold, the coefficient basis must be the base rate while the filter runs
at the multiplied rate. Sections 2 and 5 show both are `processingRate`.

```text
required for the candidate   coefficients at baseRate,  filter at baseRate x factor
observed in the authority    coefficients at processingRate, filter at processingRate
```

**H-6 verdict: NOT SUPPORTED by the new authority. The candidate's precondition is
absent.**

## 8. H-7 — does the `sr > 384000` fallback still exist

**No.** The removal is recorded in place, and the current guard is different.

```text
src\eqprocessor\EQProcessor.Coefficients.cpp
  L66334   EQCoeffsBiquad EQProcessor::calcBiquadCoeffs(..., double sr) noexcept
  L66336       // パラメータ検証 (Parameter Validation)
  L66337       // [FIX] 上限チェックを削除: 以前の sr > 384000.0 は誤り。
  L66338       // オーバーサンプリング使用時 (例: 96kHz × 8 = 768kHz) にsr=48000へフォールバックし、
  L66339       // zCache (処理srベース) とbiquad係数 (48kHzベース) が不整合になり、
  L66340       // 表示曲線のピーク周波数が最大16倍ずれる不具合を引き起こしていた。
  L66341       // (例: 100Hz設定 → 1600Hz表示、ユーザー報告: 25-100Hzブーストが800Hz付近に表示)
  L66342       // Biquad計算式はsr > 0.0であれば任意のサンプルレートで数学的に正確に動作する。
  L66343       if (sr <= 0.0 || !std::isfinite(sr))
  L66346           sr = 48000.0;
```

The remaining `sr = 48000.0` at L66346 is reached only for a non-positive or
non-finite rate, not for a high one. The SVF entry point is stricter still:

```text
  L66304   if (sr <= 0.0)  ->  bypass coefficients       (calcSVFCoeffs)
```

**H-7 verdict: the fallback is absent from the new authority. The quoted comment
is present verbatim at L66337-L66341, in the file the historical record named.**

## 9. H-9 — can the 16× rate-domain incoherence still hold

The historical mechanism required two things: a fallback that substituted one rate
for another, and a coefficient basis that diverged from the processing rate.

```text
fallback present?                        NO   (section 8)
coefficient basis == processing rate?    YES  (sections 2, 5)
zCache domain == coefficient domain?     YES  (section 5)
```

**H-9 verdict: the incoherence cannot hold in the new authority. Both of its
necessary conditions are absent.**

## 10. Specification axis, examined separately

`source behaviour ≠ specification ≠ bug verdict`. This axis was examined on its
own.

### 10.1 Parameter semantics found

```text
  freq      Hz      (L66315  const double f = static_cast<double>(freq);)
  gainDb    dB      (L66316  A = pow(10, gainDb/40) at L66672)
  q         Q       (L66674  k = 1/(q*A) — dimensionless, no rate term)
  sr        the rate the filter will run at; the multiplier is the caller's
            responsibility (L66553, L68093)
```

### 10.2 Explicit design intent found

```text
  L5757   実際の音声処理は TPT SVF (calcSVFCoeffs) を使用しており
  L5760   以前の calcBiquadCoeffs (RBJ Cookbook: alpha = sin(w0)/(2Q)) は
          実際の SVF フィルタとバンド幅が微妙に異なり
  L5762   総合応答曲線が個別バンド曲線の積と一致しないという表示上の誤りが生じていた
  L5766   calcSVFCoeffs → svfToDisplayBiquad のパスは SVF の z 域伝達関数を
          厳密に等価 biquad へ変換する（updateEQData の個別バンド曲線と同一）
  L5768   これにより「総合曲線 = 個別バンド曲線の積 = 実際の DSP 処理」が三者完全一致する
```

The stated intent is that the **DSP is the reference** and the display must agree
with it.

### 10.3 What was NOT found

```text
no statement that "a band specified at F Hz with gain G dB must present G dB at
F Hz for every oversampling factor" appears as a normative requirement.

no specification document, design contract, or test expectation asserting
EQ gain at a specified frequency as a function of the oversampling factor
was located in the authority.
```

The parameter semantics *imply* OS-independence, because the design rate and the
running rate are the same value. That is an implication of the implementation's
own contract, not an independently stated requirement.

**Specification verdict: IMPLICIT ONLY. The requirement is entailed by the
parameter semantics and the display/DSP intent, but it is not stated normatively
anywhere located in this audit.**
