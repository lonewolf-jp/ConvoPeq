## 1. 判断 1 — CI 共有ランナーで 10 ms/s を適用できるか

### 判断: **C（CI での性能判定を保留する）**

### 根拠（実測）

GitHub ホステッドランナー（`windows-2025-vs2026`）で、`TailLayerIntegrityTests` は **RelWithDebInfo 構成で 1 回実行され、Passed（2.13 秒）** だった（main `4d476d5c` の Sanitizer CI、ASan ジョブの ctest 57 件のうち #49）。

| 仕様 §3.3 の要求 | 共有ランナーでの実測 | 判定 |
| --- | --- | --- |
| MSVC Release x64 | **RelWithDebInfo**（LTCG なし、`/MD`）。当該テストは ASan 対象外 | **不一致** |
| 1 スレッド | ctest は直列実行（`-j` なし） | 一致 |
| 他プロセスの負荷を排除 | 共有ランナー。測定条件の担保なし | **不一致** |
| 複数回の測定結果 | **1 回のみ**。ctest は成功時に標準出力を出さないため **RES-F の数値が残っていない** | **不足** |
| 負荷状況に対する安定性 | 未確認 | **不足** |

`windows-msvc-build.yml` の `workflow_dispatch` は Release で ctest を実行するが、対象は `HeadlessAudioPathVerification` と `AudioEngineHarness` に限定されており、`TailLayerIntegrityTests` の数値は取れない。数値を取るには CI の変更が必要で、これは実装開始承認前の制約に反する。

判断 1 の規則「条件を満たせない場合は、この選択を成立したものとして扱わない」に従い、**A（共有ランナー採用）は成立しない**。B（セルフホストランナー）は実行環境の調達が必要で、こちらでは用意できない。

### この判断で進める内容

- 機能テスト（F/H/I）とメモリ判定（RES-M）は CI で必須のまま進める
- CPU 性能判定は、**Release の性能テストとして実装・実行はする**が、**CI の必須ゲートにはしない**（結果は記録し、判定は保留と明示）
- 保留であることを、テスト出力・設計書・本記録の 3 箇所に明示する

### 保留を解除する条件（将来）

1. Release 構成で RES-F の数値を出力する CI ジョブ（例: `ctest -C Release -R '^TailLayerPerfTests$' -V`）を用意し、**5 回以上の測定値と実行環境情報**を記録できること
2. 同一ランナー上で負荷を変えた測定を行い、10 ms/s の判定が安定することを確認できること
3. または、仕様 §3.3 の基準構成を満たすセルフホストランナーを用意できること

## 2. 判断 2 — 最悪ケースの余裕 14% を許容するか

### 判断: **C（追加測定）を実施したうえで A（現状の性能を許容する）**

### 追加測定（実施済み）

条件: 基準マシン（Intel Core i7-11700K、論理 16、Windows 11 x64）、Release ビルド、無負荷、`TailLayerIntegrityTests` を **5 回連続実行**。

測定に用いたバイナリは作業ツリーのビルド（2026-11-13 23:15）で、別タスクの未コミット変更（B-12: F-5-audio / H-4 拡張 / H-6 / H-7）を含む。ただし **RES-F の測定経路（`kCpuLimitMsPerSec`、`runCase`、`timings`、RES-F の判定式）は HEAD と同一**である（`HEAD:src/tests/TailLayerIntegrityTests.cpp` の 30〜262 行が作業ツリーと完全一致することを確認）。B-12 の差分は 304 行目以降にのみ存在し、ケース数が増えるだけで 1 ケースあたりの測定値には影響しない。

| ケース | 5 回の実測（ms/s） | 最小 / 中央値 / 最大 | 余裕（中央値基準） |
| --- | --- | ---: | ---: |
| block=64 / IR 3.0 秒（最悪） | 7.54 / 7.64 / 7.45 / 7.37 / 7.39 | **7.37 / 7.45 / 7.64** | **25%**（最大値でも 24%） |
| block=128 / IR 3.0 秒 | 5.43 / 5.35 / 5.50 / 5.36 / 5.33 | 5.33 / 5.36 / 5.50 | 45% |
| block=64 / IR 1.0 秒 | 5.40 / 5.32 / 5.33 / 5.22 / 5.26 | 5.22 / 5.32 / 5.40 | 47% |

- 5 回すべて **exit 0・RES-F 失敗 0 件**
- 最悪ケースのばらつきは 7.37〜7.64（中央値 7.45 に対して ±3.6%）
- メモリ増分は 1.00〜20.38 MB（予算 32 MB）
- プロセス CPU 時間は 5.22〜5.61 秒で、壁時計 5.24〜5.87 秒とほぼ一致（無負荷時は待ちが少ない）

先に報告した **8.62 ms/s は 1 回の測定値**で、5 回の分布（最大 7.64）から見ると上側の外れ値だった。余裕は 14% ではなく **24〜25%** が実態である。

### この判断で進める内容

- 8.62 を含む実測値を「現状の最悪ケース記録」として残す（仕様上の保証とは区別する）
- 10 ms/s の許容値は**変更しない**
- DSP 実装の性能改善は RES-F 対応の必須作業に含めない
- Release 性能テストで 10 ms/s 以下を継続的に検証し、測定値を記録する（劣化検出のため）

### 再判断の条件

性能テストの中央値が 9 ms/s を超える状態が継続した場合、または DSP 経路に変更が入った場合は、DSP 改善（Option D）の要否を再判断する。

## 3. 判断 3 — Option A″（プロセス CPU 時間への置換）を仕様改訂して採用するか

### 判断: **A（Option A″ を採用しない。現行仕様を維持する）**

### 根拠

- 仕様 §3.3 は CPU 指標を「`Add` + `Get` の**総壁時計時間** ÷ 処理した音声秒数」と明記している。置換は仕様改訂に当たる
- 判断 2 の追加測定で、無負荷時は壁時計とプロセス CPU 時間がほぼ一致した（5.24〜5.87 秒 vs 5.22〜5.61 秒）。壁時計のままでも、測定条件を統制すれば十分安定する
- 負荷時の不安定性は、指標の置換ではなく **測定環境の分離**（性能テストの専用実行、`RUN_SERIAL`）と **外乱検出・再測定**（壁時計 / CPU 時間比）で扱える
- 閾値 10 ms/s の意味を変えずに済む（指標を変えると 10 ms/s の再評価が必要になる）

### この判断で進める内容

- CPU 指標は総壁時計時間のまま
- 仕様 §3.3 の測定条件（Release x64、1 スレッド、ウォームアップ除外、5 回の中央値）に実装を合わせる（Option A′）
- プロセス CPU 時間は**診断値**としてのみ記録する（判定には使わない）
- Option A″ は未承認事項として設計書に残す
