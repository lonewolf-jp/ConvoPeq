## 0. 結論（要約）

RES-F の失敗は、DSP 処理そのものが予算を超えているためではない。**壁時計による 1 回 0.75〜26 ms の短時間測定**と、**Debug 構成で同じ予算を評価していること**、および**実行環境の外乱**が主因である。

| 事実 | 実測値 |
| --- | --- |
| Release 単独・無負荷の最悪ケース | 8.62 ms/s（予算 10、余裕 14%） |
| 同一バイナリ・外部 CPU 負荷時の最悪ケース（block=64 / IR 3.0 秒） | 10.57〜11.06 ms/s → **3/3 失敗** |
| Debug 単独・無負荷 | 21.3〜33.6 ms/s（Release の 1.7〜4.9 倍、中央値 3.1 倍） |
| 測定窓の長さ | 0.75〜26 ms（30 ケース中 27 ケースが 15.6 ms 未満） |
| メモリ増分 | 最大 20.94 MB（予算 32 MB、余裕あり） |

推奨は **Option C（Release 専用の性能テストへ分離）＋ Option A′（仕様 §3.3 に準拠した計測へ修正）＋ Option B（Debug の CPU 評価を SKIP と明示）** の組み合わせである。**10 ms/s の予算は変更しない**。DSP 実装の性能改善（Option D）は現時点では不要と判断する。

**仕様原文の確認結果（重要）**: `doc/work113/20261109-1500_実装準備仕様/report.md` §3.3 を確認した。仕様は「**MSVC Release x64、1 スレッド、同一マシン。CPU は他プロセスの負荷を排除した状態で測る**」を基準構成とし、CPU は「`Add` + `Get` の**総壁時計時間** ÷ 処理した音声秒数。**5 回の中央値（初回のウォームアップは除外）**」と定義している。この確認により、次の 2 点が確定した。

- Debug の CPU 評価を SKIP することは、仕様の基準構成（Release）に整合する（仕様外の構成で判定していたのが現状）
- **現行実装は初回ウォームアップを除外していない**（5 サンプルに初回を含めて中央値を取っている）。これは仕様 §3.3 との不一致であり、Option A′ は仕様へ戻す修正である

## 1. 現状分析

### 1.1 判定式

```cpp
// src/tests/TailLayerIntegrityTests.cpp:41-42
constexpr double kCpuLimitMsPerSec = 10.0;    // §3.3
constexpr double kMemLimitMB       = 32.0;    // §3.3

// :259-261
report ("RES-F", r.cpuMsPerAudioSec <= kCpuLimitMsPerSec && r.memDeltaMB <= kMemLimitMB,
        fmt ("block=%d ir=%d cpu=%.3f ms/s mem=%.2f MB", ...));
```

RES-F は 30 ケース（block 64〜32768 × IR 0.5 / 1.0 / 3.0 秒）で毎回判定される。1 ケースでも超えると `gFailures` が増え、`main()` は exit 1 を返す（fail-closed）。

### 1.2 CPU 測定範囲

`runCase()`（`src/tests/TailLayerIntegrityTests.cpp:131-234`）の構造は次のとおり。

| 区間 | 内容 | 測定 |
| --- | --- | --- |
| 1 | `memBefore = privateBytes()` | — |
| 2 | `MKLNonUniformConvolver conv;` 構築 | 測定外 |
| 3 | `conv.SetImpulse(...)`（IR 分割・FFT プラン生成・確保を含む） | 測定外（メモリのみ） |
| 4 | `memAfter = privateBytes()` → `memDeltaMB` | メモリ測定 |
| 5 | `in` / `out` バッファ確保 | 測定外 |
| 6 | `runOnce()` 1 回目（`t0`〜`t1`）＝ `firstMs` | **測定に含む**（5 サンプルの 1 つ） |
| 7 | `runOnce()` 4 回（各サンプル） | 測定に含む |
| 8 | 5 サンプルをソートし `timings[2]`（中央値） | — |
| 9 | `audioSec = totalLen / 48000`、`cpuMsPerAudioSec = timings[2] / audioSec` | — |

`runOnce()` は `totalLen` サンプルを block ごとに `conv.Add()` ＋ `conv.Get()` するだけである（:162-172）。したがって **測定対象は DSP の Add/Get であり、IR 生成・SetImpulse・FFT プラン生成・バッファ確保は含まれない**。測定範囲そのものは妥当で、不当に広くも狭くもない。

### 1.3 CPU 時間の取得方法

`std::chrono::steady_clock`（:175, :177, :224, :226）。Windows では QPC ベースの**壁時計**であり、プロセスまたはスレッドの CPU 時間ではない。したがって、OS のスケジューリング待ち、他プロセスの負荷、ページフォールト、クロック変動がすべて測定値に乗る。変数名は `cpuMsPerAudioSec` だが、実体は「音声 1 秒あたりの実時間」。

仕様 §3.3 も「総壁時計時間」と定めているため、壁時計であること自体は仕様どおりで欠陥ではない。問題は**測定区間の短さ**と**測定条件（他プロセスの負荷排除）が担保されていないこと**である（§1.8）。

### 1.4 メモリ測定

`privateBytes()` は `GetProcessMemoryInfo` の `PrivateUsage`（:62-70）。`SetImpulse` の直前と直後の差分を 1 回だけ取る。定常処理中の増分ではなく、コンボルバ 1 インスタンスの確保量に近い。実測は 1.97〜20.94 MB で、32 MB の予算に対する余裕は大きい。

### 1.5 実測値（無負荷・単独実行）

### 1.6 測定値のばらつきと外乱の影響

Release を 3 回連続実行した同一ケースの値と、外部負荷（論理 CPU 16 に対しビジーループ 14 本）をかけた 3 回の結果。

| 条件 | block=64 IR=3.0s | block=128 IR=3.0s | プロセス CPU 時間 | 判定 |
| --- | ---: | ---: | ---: | --- |
| 無負荷 3 回 | 7.34 / 8.04 / 8.49 | 5.94 / 6.15 / 6.36 | 5.25〜6.02 s | PASS 3/3 |
| 負荷 3 回 | 11.06 / 10.65 / 10.57 | 7.88 / — / — | 7.23〜7.55 s | **FAIL 3/3** |

同じバイナリ・同じマシンで、外部負荷の有無だけで判定が反転した。負荷時はプロセス CPU 時間自体も約 25% 増える（SMT とキャッシュ競合）が、壁時計ベースの指標はそれ以上に増える（スケジューリング待ちが加算される）。

過去の記録にも同種の事象が残っている。

- `doc/work113/20261109-2145_残件実装/report.md:277` — ASan ビルドと並行実行したときだけ RES-F が 14.3 ms/s で落ち、負荷のない ctest では通った
- 同 `:288-290` — ASan 下では RES-F の CPU が 10〜40 ms/s に増え、機能判定（F/H/I）は全通過

### 1.7 DSP 実負荷の評価

- Release 無負荷の最悪 8.62 ms/s は、**実時間の約 116 分の 1 の処理時間**に相当する。リアルタイム性の要求（1 音声秒を 1 秒以内に処理する）に対して 2 桁の余裕がある。
- block 32768 では Debug でも 1.13〜3.20 ms/s で、最適化なしでも予算内。Debug の超過は**小ブロック（64 / 128）に集中**しており、1 ブロックあたりの呼び出しオーバーヘッドが `/Od` で膨らむことが原因と整合する。
- したがって「DSP 実装が遅い」という証拠は得られていない。予算 10 ms/s は、最適化ビルドのスループットを監視する性能ガードとして機能している。

## 2. 根本原因の分類

| 分類 | 判定 | 根拠 |
| --- | --- | --- |
| 測定範囲の問題 | **部分該当** | SetImpulse は除外されており妥当。ただし 5 サンプルに初回（コールド）測定を含む |
| 測定精度・測定時間の問題 | **主因** | 壁時計 0.75〜26 ms の短時間測定。30 件中 27 件が OS タイマー分解能（既定 15.6 ms）以下。5 サンプル中央値では 1〜2 回のプリエンプションしか吸収できない |
| Debug / Release の評価条件の問題 | **主因（Debug のみ）** | `/Od` により Release の 1.7〜4.9 倍。予算 10 ms/s は最適化ビルド前提の値 |
| 実行環境・外乱の問題 | **主因（Release の ctest 失敗）** | 同一バイナリで負荷の有無により PASS/FAIL が反転（3/3） |
| DSP 実装そのものの性能問題 | **否** | Release 無負荷の最悪 8.62 ms/s は予算内。Debug の超過は小ブロックの呼び出しオーバーヘッドに由来 |
| メモリ測定の問題 | **否** | 最大 20.94 MB で予算 32 MB に対し余裕。ばらつきも小さい |
| その他 | 軽微 | `totalLen` は IR 長 + 8 ブロックのパディングを含むため、ブロックが大きいほど分母（音声秒）が膨らみ、指標が小さく出る。ケース間比較の公平性に軽い偏りがある |
| 受入仕様との不一致 | **該当（確定）** | 仕様 §3.3 は「初回のウォームアップは除外」「基準構成は MSVC Release x64」「他プロセスの負荷を排除した状態で測る」を要求するが、現行実装はいずれも満たしていない（§1.8 の表） |

**確定度**: 「測定方法と実行環境が主因」は確定（同一バイナリで負荷だけを変えて再現）。「Debug の超過が /Od 由来」は確定（ブロック依存のパターンと 1.7〜4.9 倍の比）。「DSP に性能問題なし」は Release 無負荷の実測に基づく判断で、**最悪ケースの余裕が 14% しかない**点は残る（測定の安定化後も 8〜9 ms/s 前後で推移する可能性がある）。

## 4. 推奨設計

**C ＋ A′ ＋ B の組み合わせ**を推奨する。予算 10 ms/s、対象処理（Add+Get）、F/H/I の機能判定は変更しない。A′ は仕様 §3.3 への準拠であり、閾値・指標の変更を含まない。

### 4.1 構成

| ターゲット | 構成 | 判定する受入条件 |
| --- | --- | --- |
| `TailLayerIntegrityTests`（既存） | Debug / Release 両方 | F-1〜F-5（+F-5-audio）、H-1 / H-2 / H-4 / H-6 / H-7、I-1 / I-2、**RES-M（メモリのみ）** |
| `TailLayerPerfTests`（新規） | **Release のみ** | **RES-F（CPU ≤ 10 ms/s、メモリ ≤ 32 MB）** |

- 機能テストの RES-F 行は、CPU を判定しない旨を明示して出力する（PASS と表示しない）。
  - 例: `[SKIP] RES-F-cpu block=64 ir=144000 cpu=8.62 ms/s (Debug/Release: evaluated by TailLayerPerfTests in Release)`
  - メモリは機能テスト側で従来どおり判定する（`RES-M` として出力）
- 性能テストは CTest に `CONFIGURATIONS Release` で登録し、CI の Release ジョブで必須実行する。Debug では登録されないため、`ctest -C Debug` の一覧に現れない（＝評価していないことが一覧から判別できる）。

### 4.2 計測方式（Option A′ の具体化: 仕様 §3.3 準拠）

ケースごとに次を行う（疑似コード）。壁時計のまま、仕様の「初回ウォームアップ除外」と「総時間 ÷ 総音声秒」を満たす。

```text
warmup_runs      = 1          // 仕様: 初回はウォームアップとして除外
measured_runs    = 5          // 仕様: 5 回の中央値
target_audio_sec = 5.0        // 1 回の測定で最低 5 音声秒（短時間化を防ぐ）
max_attempts     = 5          // 外乱時の再測定回数

for attempt in 1..max_attempts:
    runOnce()                                  // ウォームアップ（破棄）
    samples = []
    for k in 1..measured_runs:
        qpc0 = steady_clock.now()
        audio = 0.0
        while audio < target_audio_sec:        // 1 サンプルを十分長くする
            runOnce(); audio += audioSec
        qpc1 = steady_clock.now()
        samples.push( (qpc1 - qpc0) * 1000.0 / audio )   // ms / 音声 1 秒

    wall_ms = 試行全体（ウォームアップ + 5 サンプル）の壁時計
    cpu_ms  = 同じ区間のプロセス CPU 時間（診断・外乱判定用）
    spread  = max(samples) / min(samples)

    if wall_ms / cpu_ms <= 1.25 and spread <= 1.25:
        break                                   // 測定条件を満たす
    // 外乱。再測定し、max_attempts 回とも外乱なら FAIL（数値と理由を出力し、隠さない）

cpuMsPerAudioSec = median(samples)             // 仕様どおり 5 回の中央値
```

- **ウォームアップ除外は仕様要件**: 現行実装は 5 サンプルに初回を含めており、仕様 §3.3 の「初回のウォームアップは除外」を満たしていない。ここを直すだけでコールドコストの混入が消える。
- **1 サンプルを長くする**: 現行は 1 サンプルが 0.75〜26 ms で、30 件中 27 件が OS タイマー分解能（既定 15.6 ms）以下だった。1 サンプルを 5 音声秒以上にすると、同じ 5 回中央値でも 1 回のプリエンプションの影響が大幅に薄まる。
- **平均値で超過を隠さない**: 仕様どおり中央値を用いる。中央値・パーセンタイルで閾値を緩める設計にはしない。
- **外乱検出は 2 系統**: (1) 壁時計 / プロセス CPU 時間の比で「待たされた」ことを検出する。(2) 5 サンプルの max/min（spread）で「競合により実行速度そのものが変動した」ことを検出する。実装時の実測で、負荷時は壁時計と CPU 時間が同じだけ増えるため (1) だけでは検出できず、(2) が必要と判明した（spread は無負荷で最大 1.137、負荷時に 1.36 以上）。
- **CPU 時間は診断用**: 判定指標は仕様どおり壁時計。プロセス CPU 時間は外乱判定と記録にのみ使う（指標の置換は A″ = 仕様変更）。
- **限界（実測で確認）**: 一様な競合低下（全サンプルが同じだけ遅い）は、より遅い CPU と区別できないため検出できない。その場合は CPU 超過として FAIL する。仕様 §3.3 が要求する「他プロセスの負荷を排除した状態」は実行環境側で担保する必要がある（フェイルクローズで正しい）。

### 4.3 Debug / Release の扱い（Option B の具体化）

| 項目 | Debug | Release |
| --- | --- | --- |
| F/H/I の機能判定 | 実施 | 実施 |
| RES-M（メモリ ≤ 32 MB） | 実施 | 実施 |
| RES-F（CPU ≤ 10 ms/s） | **実施しない**（`[SKIP]` を明示出力） | `TailLayerPerfTests` で実施 |

Debug で CPU 評価を省略した事実は、テスト出力・CTest の登録一覧・設計書の 3 箇所から判別できるようにする。RES-F 全体を PASS 扱いにして CPU 評価を隠すことはしない。

仕様 §3.3 が基準構成を「MSVC Release x64」と定めているため、Debug で CPU 予算を判定しないことは仕様に整合する（現状は仕様外の構成で判定していた）。

### 4.4 CTest / CI の扱い

```cmake
# 機能テスト（既存）
add_test(NAME TailLayerIntegrityTests COMMAND TailLayerIntegrityTests)

# 性能テスト（新規・Release のみ登録）
add_test(NAME TailLayerPerfTests COMMAND TailLayerPerfTests CONFIGURATIONS Release)
set_tests_properties(TailLayerPerfTests PROPERTIES LABELS "perf")
```

- CI の Release ジョブで `ctest -C Release` を実行する限り、性能テストは必ず走る（通常の機能回帰からは外さない）。
- 性能テストを実行しない構成（Debug）では、テスト一覧に現れないこと自体が「未評価」の明示になる。
- 性能テストは並列ビルドや他テストと同時に走らせない（`RUN_SERIAL TRUE`）。過去に並行ビルド中の測定で誤 FAIL した記録がある（§1.6）。
