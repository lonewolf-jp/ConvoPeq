# F2 テストの ASan 失敗 — 原因と修正（2026-11-01）

- 発生日: main `629294a5`（doc 再生成のみのコミット）の CI
- 失敗ジョブ: `RelWithDebInfo ASan (MSVC, /MD)` → `AudioEngineHarness`（51 テスト中 1 失敗）
- 失敗テスト: `checkF2QuarantineDestroyHonoursPins`

## 1. 症状（CI ログ）

```
[F2] FAIL: deferred quarantine destroy never completed
[F2] FAIL: slot 253 was not reusable within 4 registrations (observed: 254 250 249 248)
FAIL: checkF2QuarantineDestroyHonoursPins (F2)
```

## 2. 原因（テスト側の観測方法の欠陥・製品欠陥ではない）

F2 は 2026-10-31（PR #94）で「フリーリスト順序に依存しない」形へ堅牢化したが、
**破棄の実行者**について依然として前提を置いていた。

| # | 欠陥 | 詳細 |
|---|---|---|
| **A** | 「自前の retry が破棄したこと」を要求していた | `retryDeferredQuarantineDestroy()` の戻り値が 0 だと FAIL。しかし **エンジンの reclaim tick は並行に走っており**、そちらが先に回収すると 0 を返す。ASan（低速）ではこの race が起きやすい |
| **B** | 再利用探索の上限が 4 回 | エンジンが複数の隔離スロットを回収すると、それらが LIFO で free list に積まれ、対象スロットが 4 回では届かない（観測: 254 / 250 / 249 / 248） |

A が起きると B も連鎖して失敗する（スロットが回収済みで free list の深部にあるため）。

**契約の本質は「最終状態」**であり、「どちらのスレッドが回収したか」ではない。

## 3. 修正（テストのみ）

1. **実行者を問わない**: 自前の retry と `destroyQuarantineSlot` を交互に呼びつつ、
   - pin が 0 かつ deferral が 0 になった時点で待機を終える
   - その後の **再利用性（世代 +1 で再登場）** と **冪等性（2 回目の破棄が false）** で契約を検証
2. **再利用探索の上限を 4 → 64** に拡張（free list が多数の回収分で埋まるケースに対応）。
3. 失敗時は**観測したスロット列**を出力（診断可能性の維持）。

弱体化は行っていない: 検証している性質（pin 中は再利用されない／解放後に回収される／
2 回目は no-op／世代 +1）はすべて維持している。

## 4. 別件（**製品側・要承認**）— Debug で assert 違反を観測

修正の検証中、`build-diag` **Debug** の実行で以下が出た（Release では出ない）:

```
Assertion failed: prevState == DSPState::Quarantined,
  file src\audioengine\ISRDSPHandle.cpp, line 529
```

- `destroyQuarantineSlot()` は「状態が Quarantined でなければ `false` を返す」実装だが、
  その直前で `assert` している。つまり **呼び出し側が Quarantined でないスロットを渡している**。
- 呼び出し元（製品）:
  - `AudioEngine.Commit.cpp:682`（コミット経路の隔離スロット破棄）
  - `AudioEngine.Processing.ReleaseResources.cpp:468`（shutdown ドレイン）
  - `ISRDSPHandle.cpp:606`（retry。こちらは状態を確認済みで該当しない）
- 状態確認と破棄の間に別経路（reclaim tick）が回収すると **TOCTOU** になり得る。
  Release では `false` を返して安全に処理されるが、Debug では abort するため
  **ローカル Debug 検証が中断される**（本セッションでも 2 回連続で abort）。

**提案（未実施）**: `destroyQuarantineSlot()` の `assert` を「呼び出し前の前提」ではなく
「許容される no-op」として扱う（assert を削除、または呼び出し側で状態確認）。
製品コードの変更にあたるため、**別途承認**を求める。
