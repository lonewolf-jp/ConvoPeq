## 1. R-113 — `checkSTG82OverwriteTerminalizesEvicted` の flaky

### 1.1 原因

`STG8RecoveryObligationTests.cpp` の同テストは、O1 追い出し後に
`L==1 && hasDeferred` へ到達するのを待ち（最大 60 s / 120 s）、そのあと
**固定 8 秒** `stg8SleepPump(8000)` して同じ条件を一括で再確認していた。

この 8 秒は「deferred slot が 8 秒以上保持される」ことを前提にしているが、
保持は `kDeferredPublishTTLUs`（30 秒）とパイプラインの進行に依存するため、
到達までの経過時間が長い実行では 8 秒ウィンドウ中に slot が解放され、
`L=1 hasDeferred=0` となって FAIL していた（CI: `41523395609` の run 4）。

すなわち **テストの時間依存**であり、製品の不変条件違反ではなかった
（同じ run の他の 4 回は PASS、room 全体でも再現率は低い）。

### 1.2 修正

固定 8 秒の「瞬間値」判定を、**不変条件の連続サンプリング**へ変更した。

| 監視する不変条件 | 内容 |
|---|---|
| リークなし | 8 秒間、`L <= 1` を維持（旧バグの `L=2` は即 FAIL） |
| 解放時の整合 | `hasDeferred` が false になったら、5 秒以内に `L==0`（obligation 終端）を要求 |

検証目的（O1 が残留しない／O2 の保持が壊れない）は維持し、成功条件は緩和していない
（リーク検出は強化。瞬間値の一致要求のみを、製品契約に即した「最終整合」へ置換）。

### 1.3 検証

| 項目 | 結果 |
|---|---|
| Release ビルド | 成功 |
| `AudioEngineHarness` スイート | 下記 §5 に記載 |
| 失敗率（修正前の実測） | CI の harness 実行 1 回/約 10 回で発生（`41523395609`） |

## 2. R-111 — CI 診断ステップの `CONVO_CI_BUILD`

### 2.1 前提の確認

`CMakeLists.txt` L1052-1057:

```cmake
# CI環境（CONVO_CI_BUILD定義時）は音声デバイスがないためスキップ
if(NOT DEFINED ENV{CONVO_CI_BUILD})
    add_test(NAME HeadlessAudioPathVerification COMMAND powershell ... )
endif()
```

テスト登録は **configure 時**の環境変数で決まるため、実行時ではなく
Configure ステップに設定する必要がある。

### 2.2 変更

`.github/workflows/windows-msvc-build.yml` の **release ジョブの Configure ステップ**に
`CONVO_CI_BUILD: "1"` を追加（CI 専用。ローカルのビルドスクリプトは同変数を設定しない）。

### 2.3 検証（ローカル・スクラッチ構成）

| 構成 | `ctest -N -R HeadlessAudioPathVerification` |
|---|---|
| `CONVO_CI_BUILD` 未設定 | **Total Tests: 1**（登録される） |
| `CONVO_CI_BUILD=1` | **Total Tests: 0**（登録されない） |

これにより診断ステップは `HeadlessAudioPathVerification` を実行せず、
`AudioEngineHarness` のみを実行する（音声デバイスの無いランナーで FAIL しない）。

> 注意: `CONVO_CI_BUILD` は CMakeLists L52-53 で `NUC_DEBUG_GUARDS` も有効化する。
> これは CI ビルド全体に及ぶが、ローカルビルドには影響しない（環境変数を設定しないため）。

## 3. oneAPI 導入ステップの堅牢化

### 3.1 原因

`winget install` が **非 0** を返すことがある（実測: `-1978335226`）が、
その時点で MKL/IPP のヘッダは導入済みだった。旧ステップは `$LASTEXITCODE` が
最後のネイティブコマンドの終了コードとして残るため、**成功しているのにステップが FAIL**
していた（CI: `41493867695`）。

### 3.2 変更（2 workflow 共通）

- `winget` の終了コードは**成功判定に使わない**（ログに残すだけ）
- 成功条件は **ヘッダ＋import ライブラリ**の 4 点:
  `mkl.h` / `ipp.h` / `mkl_core.lib` / `ippcore.lib`
  （ヘッダのみで無条件に成功扱いにしない）
- 不足時は不足名を列挙して **明示的に throw**（fail closed）
- 成功時は `exit 0` で終了コードを確定

### 3.3 検証

- YAML 構文: `pyyaml` で両ファイルをパースし、jobs とステップを確認
- 実挙動は CI での再実行で確認（§5）

## 4. U3 — RT 経路の新規確保の検出

### 4.1 設計

テストバイナリ（`AudioEngineHarness`）にのみリンクするプローブ。

| 要素 | 内容 |
|---|---|
| `operator new` / `delete` 置換 | `RtAllocProbe.cpp` の **1 箇所のみ**（V11 の既存実装は同ファイルへ統合し、二重定義を解消） |
| RT 区間 | `rtalloc::Scope`（thread_local 深さ）。harness の `audioLoop` が `engine_->getNextAudioBlock()` を囲む |
| 計数 | RT 区間内の確保のみ。`fetch_add` のみで確保・I/O・ロックなし |
| 既定 | **測定は OFF**（`CONVOPEQ_RT_ALLOC_PROBE=1` のときだけ `[U3]` を出力し測定モードに入る）。計数自体はスコープ内のみで無害 |
| 既存プローブ | `V11EngineRetireProtectionTests.cpp` の `a2probe` は `rtalloc` の別名へ統合（同セマンティクス） |

### 4.2 実装

- `src/tests/AudioEngineHarness/RtAllocProbe.h`（ヘッダのみ・inline）
- `src/tests/AudioEngineHarness/RtAllocProbe.cpp`（operator new/delete・環境変数解釈・出力）
- `AudioEngineHarness.cpp`: `start()` で `enableFromEnvironment()`、`audioLoop` で `RtScope`
- `PublishPipelineIntegrationTests.cpp`: `CONVOPEQ_RT_ALLOC_PROBE_RUN=<ms>` の測定モード
  （陽性対照 → 測定 → `[U3]` 出力）
- `CMakeLists.txt`: harness ターゲットへ `RtAllocProbe.cpp` を追加

### 4.3 実測（Release）

```
[U3] selfcheck_rt_alloc=1 (expect 1 when probe=on)
[U3] duration_ms=5000 blocks=4924
[U3] probe=on rt_alloc=0 rt_bytes=0 rt_max_bytes=0
```

- **陽性対照 1 件**（プローブが実際に反応すること）を確認したうえで、
- **RT 経路の新規確保は 0 件**（4,924 ブロック、5 秒）。

既定（`CONVOPEQ_RT_ALLOC_PROBE` 未設定）では `probe=off` と表示され、計数しない。
