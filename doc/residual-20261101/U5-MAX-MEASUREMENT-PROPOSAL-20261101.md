# U5 `max` 測定構造の技術提案（2026-11-01）

- 対象: R-06 U5（`RtMeasureRing` モード Full = 1 の有効化可否）
- 前提: **U5 は FAIL・既定 OFF**（2026-11-01 Owner 判断）。本提案は **設計・調査のみ**で、
  追加測定・製品コード変更・合格条件変更を承認するものではない。
- 基準: `main` = `d24a5539`。予備測定の実測データ（6 組 / 12 実行）を根拠に用いる。

---

## 1. 現行 `max` 測定の問題点

### 1.1 測定系の構成（実装の事実）

| 要素 | 実装 | 場所 |
|---|---|---|
| 測定区間 | `getNextAudioBlock()` の入口〜出口（RAII） | `AudioEngine.Processing.AudioBlock.cpp:34` |
| 開始 | `lfence` → `rdtsc` | `RtMeasureRing.h:124-128` |
| 終了 | **リング push の後**に `rdtscp` | `RtMeasureRing.h:130-134`, `:478` |
| サンプル | 1 ブロック 1 件を `SampleBuffer`（65,536 容量）へ push | `RtMeasureRing.h:319-330` |
| 集計 | 非 RT が 1 秒ごとに `collect()`、`p99` と `max` を算出 | `RtMeasureRing.h:544-`, `:650-` |
| 環境変数 | `CONVOPEQ_RT_MEASURE` 0=Off / 2=TimeOnly / 1=Full | `RtMeasureRing.h:85-90` |

ブロックは 512 サンプル。ハーネスのループはペーシング付き（測定用ドライバで 93.75 blocks/s に固定）。

### 1.2 問題点（5 点）

| # | 問題 | 実測に基づく根拠 |
|---|---|---|
| P-1 | **`max` は 32,000 ブロック中の単一最悪値**であり、その分布は裾が重い | 記録更新は 1 実行あたり **4〜9 回**、最終 `max` の確定位置は全サンプルの **6%〜96%** とばらばら（12 実行で確認） |
| P-2 | **区間が wall-clock** のため、スレッドの Descheduling（OS による横取り）も「処理時間」として計上される | 同上。`p99` は 1,250〜1,271 µs と極めて安定なのに `max` だけが 1,874〜2,393 µs まで跳ぶ |
| P-3 | **測定器自身のコストが区間内**にある（push は設計上、終了 TSC の前） | `RtMeasureRing.h:473` の push → `:478` の終了読み。意図的設計（push 費用を測るため） |
| P-4 | **`max` の推定量としての分散が大きい** | σ(Δ max) = **158.0 µs**（95% CI [98.6, 387.5]）。Δ p99 は σ = **16.8 µs**（1/9） |
| P-5 | 判定に「アーム別中央値の差 ≤ +50 µs」を使うため、**分散の大きい量の中央値を比べる**構造になっている | n=10 での中央値の 95% CI 半幅 ≈ ±870〜965 µs（v2）／±158 µs（予備、n=6 相当）。いずれも 50 µs を分解できない |

## 2. 単発遅延事象が測定値に与える影響（定量）

予備測定（無音 3 組・1 kHz 3 組）の実測:

| 実行 | p99 (µs) | max (µs) | max − p99 | 記録更新 | 最終 max の到達位置 |
|---|---|---|---|---|---|
| silence_off_1 | 1,260 | 2,065 | +805 | 7 | 11.3% |
| silence_off_2 | 1,250 | 1,874 | +624 | 4 | 6.4% |
| silence_off_3 | 1,259 | 2,013 | +754 | 6 | 83.0% |
| silence_on_1 | 1,245 | 2,071 | +826 | 5 | 95.6% |
| silence_on_2 | 1,271 | 2,157 | +886 | 6 | 42.8% |
| silence_on_3 | 1,255 | 1,971 | +716 | 5 | 18.4% |
| tone1k_off_1 | 1,631 | 2,198 | +567 | 4 | 51.9% |
| tone1k_off_2 | 1,623 | 2,314 | +691 | 7 | 65.9% |
| tone1k_off_3 | 1,631 | 2,350 | +719 | 9 | 41.9% |
| tone1k_on_1 | 1,639 | 2,268 | +629 | 7 | 58.0% |
| tone1k_on_2 | 1,621 | 2,393 | +772 | 8 | 95.6% |
| tone1k_on_3 | 1,604 | 2,154 | +550 | 5 | 16.0% |

**読み方**:

1. `max` は `p99` より **550〜886 µs 高い**。つまり `max` は「分布の肩」ではなく**独立した裾事象**を捉えている。
2. その裾事象は 1 実行に **4〜9 個**しか発生せず、**いつ発生するかは実行ごとに無作為**。
3. したがって `Δ max` は「2 本の実行から、それぞれ数個の裾事象の最大を引き当てた差」であり、
   **サンプル数 2 の比較に近い**。σ が 158 µs になるのはこの構造に起因する。
4. 対照的に `Δ p99` は σ = 16.8 µs（max の 1/9）。**同じ 32,000 サンプルから計算しているのに**
   これだけ安定するのは、p99 が 320 個のサンプルで決まるのに対し `max` は 1 個で決まるため。

## 3. 原因候補（切り分けの設計）

| 候補 | 機序 | 予想される signature | 切り分け方法 |
|---|---|---|---|
| **C-1 OS プリエンプション** | 測定スレッドが他スレッドに横取りされ、その待ち時間が区間に入る | 当該ブロックの**スレッド CPU 時間**が wall 時間より大幅に小さい | `QueryThreadCycleTime` / `GetThreadTimes` を区間外で読み、比を取る |
| **C-2 DPC / ISR（ドライバ割り込み）** | ネットワーク・GPU・オーディオドライバの DPC が同一コアで走る | 周期性がなく、特定ドライバの活動と相関 | 環境隔離（対象コアを専有）で再測定、`xperf`/ETW で DPC 時間を確認 |
| **C-3 キャッシュ汚染** | ブロック間に他スレッドが L2/L3 を汚し、次ブロックの IR 畳み込みが cold になる | `p99` は安定だが、ブロック開始直後の区間が伸びる | サブフェーズ計装（下記案 5）で「どこが伸びたか」を測る |
| **C-4 アトミック操作 / false sharing** | `read_` の acquire load が 1 秒ごとの drain で invalidate される | 1 秒に 1 回、特定ブロックだけ伸びる（周期性あり） | drain 時刻と伸びたブロックの時刻を突合 |
| **C-5 周波数遷移 / 電力管理** | ブロック間の idle で周波数が下がり、復帰に時間がかかる | 高パフォーマンス電源で消える（**実測で p99 が 5,221 → 1,255 µs に低下**） | 既に実施済み。残差が C-1/C-2/C-3 |
| **C-6 ページフォルト / アロケータ** | 初回タッチや free-list からの確保でカーネルに入る | 実行序盤に偏る、または特定世代で発生 | サブフェーズ計装＋`GetProcessMemoryInfo` の PageFaultCount 差分 |

**環境統制で C-5 は既に排除済み**（バランス → 高パフォーマンスで p99 が 1/4、max が 1/3.4）。
残るのは C-1〜C-4, C-6。予備測定の `max − p99` が 550〜886 µs で一定範囲に収まることは、
**単一の支配的要因（おそらく C-1 か C-2）**の存在を示唆する。

## 4. 測定器自身のオーバーヘッドと、測定対象との分離方法

### 4.1 現行のオーバーヘッド（1 ブロックあたり）

| 処理 | 見積り |
|---|---|
| `mode()` の atomic load（relaxed） | 〜1 ns |
| `readOrderedBegin()`（lfence + rdtsc） | 20〜30 cycles ≒ 7〜10 ns |
| `g_orderProbe` の load | 〜1 ns |
| リング push（`read_` acquire load＋24 B store＋release store） | 20〜60 ns（推定） |
| `readOrderedEnd()`（rdtscp） | 20〜30 cycles ≒ 7〜10 ns |
| `SampleBuffer::push`（1 store＋release store） | 〜5 ns |
| **合計** | **約 40〜90 ns／ブロック** |

**この値は +50 µs の 1/500〜1/1000** である。したがって「push の直接費用」が
80 µs の差を生むことは**機構的に考えにくい**。観測された差は
**裾事象の引き当て差**（C-1〜C-3）と解釈するのが自然である。

### 4.2 分離方法（3 層）

| 層 | 方法 | 何が分かるか |
|---|---|---|
| L1 区間の分離 | 終了 TSC を **push の前後で 2 回**読む（`t1` = push 前、`t2` = push 後） | `t_block = t1 − t0`（DSP 本体）と `t_push = t2 − t1`（push 費用）を**別々**に得る。push 費用の実測値が得られる |
| L2 実行状態の分離 | 区間外で `QueryThreadCycleTime` を読み、`tsc_delta` との比を取る | 当該ブロックが **走っていた**か **横取りされた**か |
| L3 サブフェーズ分離 | `getNextAudioBlock` 内の主要区間（入力取得 / グラフ構築 / 畳み込み / 出力）に任意のマーカーを置く（診断時のみ） | 伸びた 550〜886 µs がどこで発生したか |

いずれも**新しい TSC 読みは現行の区間外**に置くため、既存の測定値を歪めない。
既定（モード 0）では完全に無効。

## 5. `max` を維持したまま測定構造を改善できるか

**結論: 部分的に可能。ただし「+50 µs を判別できる」ところまでは、基準変更なしでは到達しない可能性が高い。**

### 5.1 可能な改善（基準を変えない）

| 案 | 内容 | 期待効果 | 基準への影響 |
|---|---|---|---|
| **案 1** | L2 の**原因帰属**を追加し、`max_all` と「横取りされたブロックの割合・横取り時間」を併記 | 裾の由来が判明。C-1/C-2 なら環境で改善できる | **なし**（判定は `max_all` のまま） |
| **案 2** | **環境隔離の強化**: 専用コア（SMT 兄弟を含めて隔離）、MMCSS "Pro Audio"、測定中の監視アプリ停止、Defender のスキャン除外 | σ の低減（目標 σ ≤ 64 µs）。**基準変更なしで判別可能になる唯一の筋** | **なし** |
| **案 3** | L1 の**区間分離**（push 前後で 2 回読む） | push の実費用（推定 40〜90 ns）を実測で確定。80 µs 差の説明を棄却できる | **なし**（`t_block + t_push` を従来どおり合算すれば同一量） |
| **案 4** | 実行順の**無作為化**（現状は常に OFF→ON） | 残留する順序バイアスの除去 | **なし** |
| **案 5** | L3 の**サブフェーズ計装**（診断時のみ） | 550〜886 µs の所在特定 | **なし** |

### 5.2 基準を変えずに判別するための必要反復数（現行 σ のまま）

現行規則は「アーム別中央値の差 ≤ +50 µs」。中央値差の標準誤差は
`√2 × 1.253 × σ / √n`。

| σ | ±50 µs を 95% で判定するのに必要な組数 | 実時間（1 組 = 2 実行 × 6.1 分） |
|---|---|---|
| 158.0 µs（実測） | **約 121 組** | **約 24.6 時間** |
| 64 µs（目標） | 約 20 組 | 約 4.1 時間 |
| 40 µs | 約 8 組 | 約 1.6 時間 |

→ **σ を下げる方が、反復を増やすより効率的**（σ が 1/2.5 になれば必要組数は 1/6.2）。

## 6. 現行基準を変更しない場合の限界

1. **判別力の不足**: σ = 158 µs のままだと、+50 µs を判定するには約 121 組（24.6 時間）が必要。
   現実的だが長く、その間の環境ドリフトが新たな交絡要因になる。
2. **`max` の定義上、外れ値の除外は不可**: Owner 指示（恣意的除外の禁止）により、
   横取りされたブロックを除外して `max` を取ることは**認められない**。
   したがって「横取りを除いた max」は**診断値としてのみ**意味を持つ。
3. **環境を完全に隔離できない**: Windows のホステッド環境では DPC/ISR をゼロにできない。
   σ の下限は環境依存で、**保証はできない**。
4. **「効果なし」の証明はできない**: 現行規則は「+50 µs を超えない」ことの証明を要求するが、
   裾事象の分布は裾指数に依存し、有限標本では上限を保証できない。
   これは統計的検出力の問題であり、**基準の性質**である（測定構造の改善では解消しない）。

## 8. 推奨（Owner 判断用）

1. **案 3（区間分離）と案 1（原因帰属）を実装**する。どちらも**合格条件を変えない**。
   - これにより「push の実費用」と「裾の由来」が実測で確定する。
   - 80 µs の差が push 由来でないことが示されれば、U5 の問いの立て方自体を見直す根拠になる。
2. **案 2（環境隔離）を同時に実施**し、σ が 64 µs 以下になるかを測る。
   - 達成できれば、**現行規則のまま** n=10〜20 組で判定可能になる。
3. **案 4（無作為化）**はコストがほぼゼロのため併せて実施。
4. **案 5（サブフェーズ）**は 550〜886 µs の所在が案 1 で説明できない場合に限り実施。
5. **案 6（指標の再定義）は提案しない**。必要になった場合は、本提案とは独立の承認事項として扱う。

**上記はいずれも未実施。U5 は FAIL・既定 OFF、追加測定は未承認のまま維持する。**
