- 基準: `main` = `origin/main` = `26fffaa2`（2026-11-05 時点）

## 1. RES2-01 ポリフェーズ利得規約の不対称（案 E）

### 1.1 現行ソースに基づく問題

- `src/CustomInputOversampler.cpp:556-561` で `convValue *= 2.0` のみ適用され、`centerValue *= 2.0` は `CONVOPEQ_CORRECT_POLYPHASE_GAIN` の内側（既定 OFF）。
- 分岐係数和が 1.0 と 0.5 で不対称。up/down 往復の DC 利得は 0.75^N（N は段数）。
- 有効化した場合の実測（P1-1／P1-3、`doc/work113/p1_4_adoption_decision_package_20260922.md`）:
  - 出力 +2.4988 / +4.9975 / +7.4963 dB（2x／4x／8x）
  - SoftClip drive 0.0018〜0.0687 → 0.0182〜0.1473（5〜10 倍）
  - limiter 到達 0 → 119/4096（os≥2・0 dBFS）
  - hard clamp 0 件、latency 不変、float/double 一致
- 0.75^N を打ち消す補償は production に存在しない（P1-2）。
- **設計意図だったかは未確定**（P1-4 の N1）。「バグである」とは断定できない。

### 1.2 放置した場合のリスク

- 既定設定の出力レベルが OS 倍率に依存して 0.75^N 低いまま（例: 8x で約 −7.5 dB 相当）。
- ユーザーが makeup で補正している場合、将来の採用時に二重補償となる。
- ただし現状で破綻・クラッシュはない。

### 1.3 推奨対応案

**保留（既定 OFF 維持）。** 採用判断の前に、次の 3 点を埋める。

1. 聴感評価（N2）
2. 既存プリセット replay の出力比較（N4）
3. EQ boost／IR boost 併用時の挙動（N3）

### 1.4 対応案ごとの副作用・リスク

| 案 | 内容 | 副作用・リスク |
|---|---|---|
| A 保留（推奨） | 既定 OFF のまま | 現状のレベル特性が残る。ユーザー補正との二重補償リスクは将来に先送り |
| B 採用 + 既定 ON | 案 E を有効化 | 既定出力が最大 +7.5 dB 変化、limiter 到達が増える。プリセットの体感が変わる |
| C 採用 + 既定 OFF | コードだけ採用し flag は OFF | 実質 A と同じ。判断が先送りされるだけ |
| D 却下（現状を仕様化） | 0.75^N を仕様として文書化 | 将来の不具合報告時に「意図的」と説明できるが、利得規約の不対称は残る |

### 1.5 必要な権限

音声出力の仕様変更にあたるため、**Owner の明示承認**。

### 1.6 検証方法

`PolyphaseGainFidelityTests`（OFF/ON の REF-FIDELITY）、`P1PolyphaseGainCharacterization`（`--p1-char`）、latency 不変、hard clamp 0、聴感評価、preset replay 比較。

### 1.7 Owner に求める判断

- **D1**: 案 E を採用するか。
- **D2**: 採用する場合、既定 ON にするか（聴感・preset データが前提）。
- **D3**: 不採用の場合、0.75^N を仕様として文書化してクローズするか。

## 2. RES2-04 F-4 / D2b 記録消失

### 2.1 現行ソースに基づく問題

- 記録消失（`overwrite` / `recSeq` / `redrive`）の事象。D2b 診断タプルは main に存在し `[D2B-SELFCHECK] PASS`。
- 2026-11-01 の調査で 38 反復すべて `overwrite=1/recSeq=0/redrive=0` の一定値。再現せず、Owner 判断で停止。

### 2.2 放置した場合のリスク

- 発生すれば記録系の信頼性に影響。ただし現行の再現試験では観測されていない。
- 診断は残っているため、発生時の切り分けは可能。

### 2.3 推奨対応案

**停止継続。** 新証拠（ユーザー報告・ログ・時系列）が出た時のみ再開する。

### 2.4 対応案ごとの副作用・リスク

| 案 | 内容 | 副作用・リスク |
|---|---|---|
| A 停止継続（推奨） | 現状維持 | 潜在事象は未解明のまま |
| B 再開（再現試験の拡大） | 反復回数・環境を増やす | 工数増。再現しないまま終わる可能性 |
| C 診断の常時有効化 | 記録経路の診断を既定で有効化 | ログ量増加、RT 負荷に注意 |
| D クローズ（再現しない合意） | 監視のみで終了 | 将来の同種報告時に再調査が必要 |

### 2.5 必要な権限

再開する場合は **Owner の明示承認**。

### 2.6 検証方法

再現手順の確立、`[D2B-SELFCHECK]`、反復試験の統計（同一条件で N 回）。

### 2.7 Owner に求める判断

- 停止継続でよいか。
- 再開する場合の許容工数と対象環境。

## 5. RES2-07 U5（実時間計測モードの製品有効化）

### 5.1 現行ソースに基づく問題

- 計測器は `RtMeasureRing` に実装され、既定は `Mode::Off`（`RtMeasureRing.h:97`）。`initializeFromEnvironment()` で環境変数から有効化する。
- 測定は metric v2（p99 非劣性＋周期超過ゲート）で **PASS**（PR #119、24/24 有効）。
- 製品としての有効化（UI からの切替・既定 ON）は未実装／未承認。

### 5.2 放置した場合のリスク

- ユーザーは実時間計測の恩恵を受けられない（現状の既定動作に影響はない）。
- 有効化する場合、RT 経路の追加コストと、計測値の解釈（環境依存）を説明する必要がある。

### 5.3 推奨対応案

**既定 OFF を継続。** 有効化するなら、次を前提にする。

1. UI からの明示的な切替（既定は OFF）
2. 有効化時の RT オーバーヘッド測定
3. 計測値の説明（環境依存であること）

### 5.4 対応案ごとの副作用・リスク

| 案 | 内容 | 副作用・リスク |
|---|---|---|
| A 既定 OFF 継続（推奨） | 現状維持 | 機能は提供されない |
| B UI 切替で任意有効化 | 既定 OFF＋ユーザー操作 | UI・設定の追加、サポート説明が必要 |
| C 既定 ON | 常時計測 | 全ユーザーの RT 負荷増、環境差で誤解を招く |

### 5.5 必要な権限

**U5 の製品有効化は Owner の明示承認**（既定 OFF の維持は現状どおり）。

### 5.6 検証方法

RT 回帰、オーバーヘッド、metric v2 の再現、UI 切替の動作確認。

### 5.7 Owner に求める判断

- 既定 OFF を継続するか。
- UI 切替を実装するか（実装する場合の既定は OFF）。

## 6. RES2-12 soak のスケジュール化

### 6.1 現行ソースに基づく問題

- `.github/workflows/soak-ci.yml` は `workflow_dispatch` のみ。S1/S2b/S3/S4/S5 の長時間シナリオは手動実行。
- 設計方針（work91 §6）でも「push ごとの CI には載せない」と明記。

### 6.2 放置した場合のリスク

- 長時間・高負荷の退行が、手動実行するまで検出されない。
- リリース直前に発見される可能性。

### 6.3 推奨対応案

**夜間のスケジュール実行（例: 週 1 回）を推奨。** 失敗時は Issue ではなく通知に留め、PR をブロックしない。

### 6.4 対応案ごとの副作用・リスク

| 案 | 内容 | 副作用・リスク |
|---|---|---|
| A 現状維持（手動） | 変更なし | 退行の検出が遅れる |
| B 週 1 回スケジュール（推奨） | cron + 通知 | ランナー時間の消費、フレーク時の調査コスト |
| C push ごとに実行 | 常時 | CI 時間が大幅増、開発速度低下 |

### 6.5 必要な権限

運用コストを伴うため **Owner 判断**（CI 定義変更は承認範囲内だが、実行頻度は運用判断）。

### 6.6 検証方法

1 回の通し実行時間、成功率、失敗時の通知経路。

### 6.7 Owner に求める判断

- スケジュール化するか、頻度はどれくらいか。
- 失敗時に PR をブロックするか、通知のみか。
